# `#51` 팀 공유글

> 2026-10-27 승조 작성 원문. 슬랙 · 스크럼에 그대로 붙이는 글이라 **꾸밈 없이 둔다**.
> 숫자 정본은 [`results.md`](results.md), 결정 과정은 [`research.md`](research.md).

```
문제

에이전트를 붙였을 때 주문 1건당

CPU : 16.61ms -> 19.98ms (20% 증가)

요청 1건당으로 보면 11.06 -> 13.30 (주문 1건은 요청 1.502건)

메모리 : 서비스마다 75~126MB 증가

그래서 하려는 것은 뭔가?

위 측정결과 줄일 수 있을까?
줄이는 법은 무엇이고 각각 얼마가 줄었나?

줄일 수 있는 파트들과 각각에 대한 기대

메트릭 전송 간격 (10초 -> 30초 -> 60초)

에이전트는 메트릭을 모아 뒀다가 간격마다 한 번에 보내는 방식
간격을 늘리면 보내는 횟수가 줄어서 CPU 가 줄 것이라고 기대

적는 일은 그대로 두고 보내는 횟수만 줄이는

셋 다 쟀다 (10초가 디폴트 값, 30초와 60초가 변형)

트레이스 샘플링 (100% -> 10% -> 1%)

에이전트가 만든 스팬을 보낼지 말지 비율로 정한다
보내는 양이 줄어서 CPU 와 메모리가 줄 것이라고 기대
바꾼 것은 앱 쪽 샘플러(collector 쪽이 아님)

운영 비율 1% 는 collector 쪽에서 받은 뒤 버리는 다른 층이라 이번 범위가 아니다

배치 크기와 주기 (묶음 512 -> 1024 · 주기 5초 -> 10초)

한 번에 더 많이 + 더 드물게 보내면 보내는 횟수가 줄어서 CPU 가 줄 것이라고 기대
다만 쌓아 두는 칸(큐 2048)을 키우면 메모리가 늘 수 있어서 큐는 가만히

에이전트가 들여다보는 범위

현재 : 라이브러리를 전부 켜 두고 다 본다
쇼핑몰이 실제로 사용하는 것만 켜면 CPU 와 메모리 둘 다 줄 것이라고 기대
켜 둔 것 : 들어오는 요청, 서비스 사이 호출, MySQL, Redis, 로그 보내기, JVM 지표, 스레드를 지나는 문맥 전파 등
과거 3회차로 이미 본 변형이고 이번에 5회차로 늘려 다시 쟀다

어떻게 쟀나

변형 여덟가지를 85회차 돌림
(회차 : 쇼핑몰 띄우기-> 워밍업 40초-> 60초 동안 재고 내리는 것을 한 번)

초당 20건 70회차 + 초당 40건 15회차 · k6 실패 0건
반복마다 변형 순서를 한 칸 돌려서 기계 발열과 주문 표 쌓임이 한쪽에 몰리지 않게

e.g. 1~4회차   off -> on -> i30 -> i60,  5~8회차   on -> i30 -> i60 -> off

윈도우는 60초로 고정

전송 간격(설정값)과 재는 창(60초)은 다른 것

결과

CPU 쪽에선 딱히 줄일 수 있는 게 없었다

보내는 양을 91배 줄였는데 CPU 가 그대로였담

메모리는 사용하지 않은 라이브러리를 줄이면 각 서비스 마다 20MB 정도 줄일 수 있담
```

## 이 글에 일부러 안 넣은 것

공유글은 짧게 두고 아래는 `results.md` 로 미뤘다. 질문이 오면 그쪽을 가리킨다.

- **계측 범위를 줄이는 대가** : 메트릭 84건이 빠진다 (커넥션 풀 지표 · 로그에 추적 아이디 끼우기)
- **20MB 가 두 서비스에서만 확인됐다** : order · inventory 는 폭이 안 겹치고 gateway · payment 는 겹친다
- **지금은 기준에 통과한다** : ADR `#56`(1코어 대비 +3%p · 150MB) 대비 +0.9 ~ 2.1%p · 최대 126MB
- **기준을 못 지키게 되면 길이 셋뿐이다** : 파드 한도를 올리거나 · 보는 범위를 줄이거나 · 에이전트를 뗀다
