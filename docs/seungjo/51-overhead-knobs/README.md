## 문제

`#36` 이 "에이전트를 붙이면 주문 1건당 CPU 가 약 20% 늘고 서비스마다 메모리가 최대 141MB 늘어난다" 를 쟀다. 멘토가 그 다음을 물었다. **"줄이는 법은 무엇이고 각각 얼마를 줄이나."**

- 후보는 넷이었다 : 계측 범위 · 메트릭 전송 간격 · 트레이스 샘플링 · 배치 크기와 큐
- 넷 중 **배치 설정은 두 레포 전체에서 0건**이라 기본값으로 돌고 있었고, 그 기본값이 무엇인지도 몰랐다
- `#36` 이 남긴 약점 : 원인 찾기 실험을 **3회 · 번갈아 안 돌림**으로 해서 단정하지 못했다

## 선택지

변형끼리 흔들림에 묻혀 안 갈릴 수 있다는 것이 갈림길이었다.

| 방법 | 장점 | 단점 |
|---|---|---|
| A 회차 늘리기 | 다른 것을 안 건드린다. 중앙값이 튀는 회차를 눌러 준다 | 시간이 든다. **치우친 값이면 회차를 늘려도 안 갈린다** |
| B 측정 창 늘리기 | 창 안의 전송 횟수가 늘어 편차가 작아진다 | 회차당 시간이 통째로 늘어난다 |
| C 전송 간격에 맞춰 창 조절 | 간격마다 전송 횟수를 같게 맞출 수 있다 | 변형마다 창이 달라져 나란히 못 놓는다 |
| D 부하 올리기 | 신호가 커져 차이가 보인다 | 기계가 포화되면 다른 이유로 흔들린다 |
| E 전송 횟수를 같이 기록 | **흔들림인지 치우침인지 가릴 수 있다** | 수집기를 띄워 둬야 한다 |

## 결정

- **고른 것** : **A + E**. 전송 간격 묶음만 10회차(`#36` 이 3회로 못 단정한 자리라 그 2배 넘게), 나머지는 5회차(`#36` 본 실험과 같게). **반복마다 변형 순서를 한 칸 돌린다**
- **D 는 버렸다가 결국 검산에 썼다** : 1차 70회차에서 변형끼리 전혀 안 갈려 부하를 두 배로 올려 폭을 좁혀 봐야 했다
- **되돌리는 조건** : 에이전트 버전을 올리거나 · 쇼핑몰에 실제 업무 로직이 붙거나 · k8s 파드 limit 이 정해지면 같은 스크립트로 다시 잰다

결정 원문은 [`research.md`](research.md) 6 · 8 절과 [`prompts.md`](prompts.md).

## 결과

자세한 표는 [`results.md`](results.md), 원자료 [`results.csv`](results.csv).

| 설정 | 기대 | 실제 CPU | 실제 메모리 |
|---|---|---|---|
| 메트릭 전송 간격 10초 → 30 · 60초 | CPU | **안 줄었다** | 안 줄었다 |
| 트레이스 샘플링 100% → 10 · 1% | CPU · 메모리 | **안 줄었다** | 안 줄었다 |
| 배치 묶음 512 → 1024 · 주기 5 → 10초 | CPU | **안 줄었다** | 안 줄었다 |
| 계측 범위 줄이기 | CPU · 메모리 | 안 줄었다 | **약 20MB 줄었다** |

- **뗌과 붙임은 갈리고 변형끼리는 안 갈린다** : 뗌 최대 11.64ms < 붙임 최소 12.34ms 인데, 붙임 변형 여덟의 폭은 12.3 ~ 14.2 로 전부 겹친다
- **왜 안 줄었나는 받은 건수가 답을 줬다** : 메트릭 쇼핑몰 몫이 558 : 186 : 93 = 6 : 2 : 1 로 간격의 역수 그대로 줄었고, 스팬은 20,608 → 226 으로 약 91배 줄었다. **보내는 양을 91배 줄였는데 CPU 가 그대로**라 비용은 보내기가 아니라 **계측 자체**에 있다
- **`#36` 과 합쳐야 짚힌다** : `#36` 의 `metrics-off`(적는 것까지 끔)는 CPU 의 약 5분의 1 을 가져갔는데 이번 `interval`(보내는 횟수만 줄임)은 0 을 가져갔다. **적는 일은 비용이고 보내는 일은 비용이 아니다**
- **계측 범위 줄이기는 `#36` 의 10 ~ 20MB 를 굳힌 것**이다(3회차 → 5회차, 폭이 안 겹치는 것까지). 발견이 아니라 확인이다. 다만 **메트릭 84건이 빠진다**(`#36` 이 짚은 커넥션 풀 지표 · 로그 MDC 주입)

## 어떻게 확인했나

- 회차 **85번** : 초당 20건 70회차(`interval` 40 · `rest` 30) + 초당 40건 15회차(`check`). k6 check 실패 **0건** · 요청 수가 모자라 버린 회차 **0건**
- **판을 먼저 검증했다** : 뗌 1회 · 붙임 1회를 돌려 CSV 네 줄 · `recv_traces` 0 과 20,624 를 확인한 뒤 본 측정에 들어갔다(그 두 회차는 `out/smoke-2026-10-27.csv` 로 따로 뺐다)
- **배치 기본값을 jar 에서 직접 읽었다** : 디버그 로그에 안 찍혀 `javap -p -constants` 로 상수를 봤다. 묶음 512 · 큐 2048 · 주기 5,000ms · 전송 제한 30,000ms (로그 쪽 주기 1,000ms)
- **변형 여섯이 실제로 실리는지 `docker compose config` 로 확인**했다
- **묶음 스크립트를 가짜 `run.sh` 로 미리 돌려** 40 · 30 · 10 회차가 계획과 맞는 것을 확인했다
- **측정 직전에 함정을 밟았다** : `#36` 때 쓴 `out/results.csv` 가 남아 있어 열 10개인 옛 머리가 유지되고 새 회차만 열 12개로 붙었다. `run.sh` 가 머리를 검사해 **도커를 올리기 전에 멈추게** 고쳤고 옛 머리 파일로 시험해 확인했다
- **`#36` 과 다른 조건 하나** : 측정 동안 로컬 k8s 클러스터(deploy `#20` 연습판)가 같이 떠 있었다(1코어의 약 0.16). 변형끼리는 같은 조건에서 번갈아 돌렸으므로 비교는 성립하지만 **`#36` 의 절대값과 나란히 놓지 않는다**

## 이 이슈에서 배운 것 (세 줄)

- **적는 일은 비용이고 보내는 일은 비용이 아니다** : 전송량을 91배 줄여 놓고 CPU 가 그대로인 것을 봤다
- **폭을 안 재면 중앙값 순위는 거짓말을 한다** : 중앙값만 보면 설정을 줄인 쪽이 더 비싸 보였는데 회차 폭이 전부 겹쳤다
- **예상과 반대 결과도 결과다** : 여섯 변형 중 하나도 CPU 를 안 줄였지만 「무엇을 해도 안 된다」가 멘토 질문의 답이 됐다
