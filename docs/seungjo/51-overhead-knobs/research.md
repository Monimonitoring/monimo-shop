## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : `#36` 이 「지금 설정이 얼마나 비싼가」를 쟀고 **고친 기준으로도 초당 40건이면 CPU 가 넘고 메모리는 최대 +141MB 로 경계**라는 결과가 나왔다. 그런데 「그러면 어떻게 줄이나」는 재지 않았다. 줄일 수 있는 설정이 넷 있는데 각각 얼마가 주는지 숫자가 없다
- **그래서 무엇을 만드나** : 설정 네 개(**계측 범위 · 메트릭 전송 간격 · 트레이스 샘플링 · 배치 크기와 큐**)를 하나씩 바꿔 `#36` 과 **같은 방식**으로 CPU %p 와 메모리 MB 를 잰다. 그리고 설정마다 **무엇을 잃나**(화면에서 무엇이 비거나 늦어지나)를 같이 적어 **운영에 넣을 값 한 벌**을 낸다
- **안 하면 어떻게 되나** : 배포 5~6단계에서 EKS 매니페스트에 넣을 숫자를 **근거 없이 고르게 된다**. 그리고 결과물을 읽는 사람 눈에는 「비용을 쟀다」로 끝나 「그래서 어떻게 줄이나」에 답이 없다 (멘토 피드백 C 가 가리킨 자리)

| | |
|---|---|
| 건드리는 모듈 · 파일 | `perf/overhead/` 에 변형 `.yml` 을 더하고 `run.sh` 의 변형 목록 · `suite.sh` 회차 표 · `summarize.py` 출력에 그 변형을 넣는다 · 하네스 `README.md` 변형 표 · 이 폴더 문서 넷 |

**조사 들어가기 전에 내가 알던 것 (세 줄)**

- `#36` 에서 **샘플링 10% 는 CPU 를 거의 못 줄였다**. 계측은 샘플링 결정보다 먼저 돌고, HTTP · DB 지연 히스토그램은 샘플링과 상관없이 모든 요청에 기록된다
- **메모리 +80~141MB 중 45~55MB 는 힙 아닌 쪽**(에이전트 클래스 약 5,000개 · JIT 코드)이라 설정으로는 안 준다. 설정으로 줄 수 있는 것은 그 위에 얹힌 힙 쪽이다
- **쓰는 계측만 켜면 메모리가 10~20MB 줄었다**. CPU 차이는 흔들림 안에 묻혀 단정하지 못했다

**알고 싶었던 것** (다섯)

- ① **무엇이 실제로 듣나** : 설정 넷 중 CPU 를 줄이는 것과 메모리를 줄이는 것이 갈리나. `#36` 이 「메트릭 기록이 CPU 증가의 약 1/5」을 3회로만 봤는데 전송 간격을 늘리면 그게 숫자로 확인되나
- ② **전송 간격을 늘리면 CPU 가 정말 주나** : 메트릭 비용이 「기록」과 「전송」 둘로 나뉘는데, 간격은 **전송만** 늦춘다. 기록이 비용의 대부분이면 간격을 60초로 늘려도 CPU 가 안 줄 수 있다
- ③ **배치 크기를 키우면 메모리가 늘지 않나** : 큐를 키우면 안 보낸 스팬이 더 오래 메모리에 남는다. CPU 는 줄고 메모리는 늘어 **서로 반대로 움직이는 설정**인지 확인해야 한다
- ④ **설정마다 무엇을 잃나** : 전송 간격 60초는 **이미 관측된 문제**가 있다(backend `#238`, 아래 2.5). 샘플링을 1% 로 내리면 화면의 트레이스 표본이 얼마나 비나. 계측을 줄이면 Service map 간선이 사라지나
- ⑤ **운영 권고값을 어떤 부하 기준으로 정하나** : `#36` 판정은 초당 20건 기준이고 40건에서는 넘었다. 운영 예상은 초당 주문 20건(backend `20-scope.md` 역산)이라 **권고값이 40건에서도 버티는지**까지 봐야 하나

## 2. 작업하기 전에 알아야 하는 것

### 2.1 데이터는 어디로 흐르나 (앱 JVM 안에서 네 단계)

에이전트가 하는 일을 네 단계로 나눠 두면 각 설정이 어느 단계에 붙는지 보인다.

```
① 계측          앱 메서드에 끼어들어 스팬을 만들고 히스토그램에 값을 적는다
                  (요청마다 돈다. 샘플링 결정보다 먼저다)
      ↓
② 샘플링 결정    이 트레이스를 남길까 버릴까를 trace_id 로 정한다
                  (버려도 ① 은 이미 돌았다)
      ↓
③ 배치 큐        남길 스팬을 큐에 쌓아 두고 묶음이 차거나 시간이 되면 꺼낸다
                  (메모리에 머문다)
      ↓
④ 전송           OTLP gRPC 로 Collector 에 보낸다
                  (네트워크 · 직렬화 CPU)
```

- 메트릭은 ① 에서 **적고**(히스토그램 칸 더하기) ④ 에서 **보낸다**(주기마다 한 번)
  - **적기** : 요청이 올 때마다 메모리에 있는 칸을 갱신한다. 예로 응답이 23ms 였으면 「20~25ms 칸」을 +1 한다. **요청 수만큼** 일어난다
  - **보내기** : 주기마다 그 칸들을 한 번 떠서(스냅샷) OTLP 로 넘긴다. **주기 수만큼** 일어난다
  - 초당 20건 · 60초면 **적기는 1,200번 이상**(요청 하나가 여러 지표를 건드린다)이고 **보내기는 10초 간격에서 6번**이다. 그래서 간격을 늘려도 CPU 가 거의 안 줄 수 있다 (알고 싶었던 것 ②)
- **지표가 두 종류라 간격이 미치는 범위가 다르다**
  - **요청마다 적는 것** (HTTP · DB 지연 히스토그램) : 간격을 늘려도 **적는 횟수는 그대로**다
  - **내보낼 때 읽는 것** (`jvm.memory.used` 같은 게이지) : 내보낼 때 값을 읽으므로 **간격을 늘리면 읽는 횟수도 준다**
  - 즉 간격을 늘려 주는 것은 **보내기 + JVM 게이지 읽기**이고, 줄지 않는 것은 **요청마다 적기**다
- 로그도 같은 모양이다 : Logback 붙임쇠가 ① 에서 레코드를 만들고 ③ · ④ 로 간다

### 2.2 조절할 설정 넷이 어느 단계를 건드리나

| 조절할 설정 | 설정 이름 | 건드리는 단계 | 기대 |
|---|---|---|---|
| 계측 범위 | `otel.instrumentation.common.default-enabled=false` + 쓰는 것만 켜기 | **①** | 안 쓰는 계측이 안 끼어드니 CPU · 메모리 둘 다 |
| 메트릭 전송 간격 | `otel.metric.export.interval` (지금 10초) | **④** | 전송 횟수가 줄어 CPU. 기록은 그대로 |
| 트레이스 샘플링 | `otel.traces.sampler` (지금 `always_on`) | **②** | ③ · ④ 가 줄어 CPU · 메모리. **① 은 안 준다** |
| 배치 크기 · 큐 | `otel.bsp.*` (큐 크기 · 묶음 크기 · 보내는 주기) | **③ · ④** | 전송 횟수가 줄어 CPU. 큐를 키우면 메모리는 **늘 수 있다** |

- **샘플링은 두 층에 있다. 이번에 바꾸는 것은 앱 쪽이다**
  - **앱 쪽** `otel.traces.sampler` (지금 `always_on`) : 에이전트가 **보낼지 말지**를 정한다. 줄이면 네트워크 · Collector 이후가 준다
  - **Collector 쪽** `application_configs.sampling_rate` (`#121` · `#206` · ADR `#72`) : 받은 뒤에 버린다. **앱 부담과는 아무 상관이 없다**
  - 이번 이슈는 **앱 쪽만** 건드린다. Collector 쪽 비율(운영 `shop` 1% · `monimo` 50%)은 배포 5~7단계 몫이다
- **지금 우리는 배치 설정을 한 번도 건드린 적이 없다** : 두 레포 전체에서 `bsp` · `blrp` 설정이 **0건**이라 에이전트 기본값으로 돈다 (grep 으로 확인)
- **기본값을 에이전트 2.31.1 jar 에서 직접 읽었다** (2026-10-27, 구현 1단계) : 스팬 쪽 `BatchSpanProcessorBuilder` 의 상수가 **묶음 512 · 큐 2048 · 주기 5,000ms · 전송 제한 시간 30,000ms** 다. 로그 쪽(`BatchLogRecordProcessorBuilder`)은 같은 값에 주기만 **1,000ms** 다
  - 읽은 방법 : 이미지에서 `opentelemetry-javaagent.jar` 를 꺼내 `inst/**/BatchSpanProcessorBuilder.classdata` 를 `.class` 로 바꾸고 `javap -p -constants` 로 상수를 봤다. **에이전트 디버그 로그에는 이 값이 안 찍힌다**(1,052줄을 받아 `otel.` 설정 이름이 `otel.javaagent` 하나뿐이었다)
  - 문서로 알던 값과 같았지만 **받아쓰지 않고 우리가 쓰는 jar 에서 확인했다** (`#144` 에서 남이 쟀다는 숫자를 받아쓴 것이 두 번 틀렸던 선례)
  - 곁들여 알게 된 것 : **메트릭 주기의 OTel 기본값은 60초**다(`PeriodicMetricReaderBuilder.DEFAULT_SCHEDULE_DELAY_MINUTES = 1`). 우리가 `agent.properties` 로 10초까지 내려 둔 것이고, 그래서 **권고 후보 30초도 라이브러리 기본값보다 짧다**

### 2.5 설정마다 무엇을 잃나 (이미 아는 것)

- **메트릭 전송 간격 60초는 이미 터진 적이 있다** : 지표가 1분 버킷으로 집계되는데 전송이 60초면 분 경계를 넘나들어 **1분이 비고 다음 1분에 2분치가 몰린다**. backend `#238` 로 열려 있고(`fix/238` PR `#239` 진행 중) `PR #224` 리뷰에서 「운영은 10~30초」를 약속해 뒀다. 그래서 **60초는 재기는 하되 권고값 후보에서 뺄 가능성이 높다**
- **샘플링을 내리면 화면 표본이 준다** : 1% 면 backend `20-scope.md` 역산으로 초당 3.4 스팬이다. 트레이스 상세는 「요청 100건 중 1건」만 보이고, Service map 간선 수는 유지되지만 **드문 경로가 안 잡힌다**
- **계측을 줄일 때 쓰는 것을 끄면 트레이스에 구멍이 난다** : `#36` 이 `instr-min` 에서 **Service map · 트레이스 스팬 모양이 그대로인지 ClickHouse `spans` 로 확인**해 뒀다. 이번에 목록을 더 줄이면 그 확인을 다시 해야 한다
- **배치를 키우면 잃는 것은 신선도다** : 보내는 주기를 늘리면 화면에 늦게 뜬다. 지금 수집 지연은 중앙 2.65초 · p95 5.1초인데 **대부분이 이미 에이전트 배치 대기**다 (backend 실측). 주기를 늘리면 그 지연이 그만큼 늘고, 탐지 `settleDelay` 30초와 경보 60초 NFR 에 닿는다

### 2.6 재는 방법은 이미 있다 (하네스)

`perf/overhead/` 가 `#36` 에서 만들어졌고 변형을 **파일 하나 더하고 `run.sh` 에 한 줄**로 늘릴 수 있다.

| 있는 것 | 무엇 |
|---|---|
| `run.sh <변형> <초당건수>` | 한 회차 : compose up → 워밍업 40초 → cgroup 읽기 → k6 60초 → cgroup 다시 → down |
| `suite.sh` | 전체 회차 (지금 약 2시간 40분) |
| `summarize.py` | 서비스별 중앙값 표 |
| `limits.yml` | 네 서비스 CPU 1개 · 메모리 1GB (모든 변형에 깔린다) |
| `no-agent.yml` | 뗀 쪽. `-javaagent` 를 **아예 뺀다** (`OTEL_JAVAAGENT_ENABLED=false` 는 jar 를 읽어 조금 남는다) |
| `metrics-off.yml` · `instr-min.yml` | 원인 찾기용 변형 |
| `nmt.yml` | 메모리를 항목별로 쪼갠다 (NMT 자체가 느려 CPU 비교엔 안 쓴다) |

- CPU 는 cgroup `cpu.stat usage_usec` 구간 차이, 메모리는 끝난 순간 `memory.current` 다. **컨테이너 바깥에서 읽으므로 에이전트가 없어도 똑같이 잰다**
- 가드가 있다 : 쇼핑몰 컨테이너가 하나라도 떠 있으면 시작하지 않고, cgroup 을 못 읽거나 k6 요청이 95% 미만이면 그 회차를 **기록하지 않고 멈춘다**
- **맥북 한 대에서 재므로 한두 회차는 튄다** : 5회 이상 번갈아 돌린 중앙값을 본다. `#36` 은 12칸 중 11칸에서 「붙임 최솟값 > 뗌 최댓값」이 되는 것으로 흔들림을 눌렀다

### 2.6.1 「60초」가 일으키는 문제는 **둘이고 서로 다르다**

읽을 때 가장 잘 섞이는 자리라 먼저 가른다. **같은 모양의 사고가 다른 두 곳에서 일어난다** : 「주기가 칸 길이와 같으면 경계에서 터진다」

| | 문제 A | 문제 B |
|---|---|---|
| 어디서 | **운영** | **우리 측정** |
| 무엇과 무엇이 같아서 | 전송 간격 60초 = **저장소의 1분 칸** | 전송 간격 60초 = **측정 창 60초** |
| 무엇이 깨지나 | 1분 칸이 비거나 2분치가 몰려 **화면 · 경보가 틀린다** | 창 안의 전송이 1번이냐 2번이냐로 **CPU 숫자가 튄다** |
| 이미 일어났나 | **그렇다** (backend `#238` · `PR #239` 가 고치는 중) | 아직 (예상) |
| 우리 대응 | 60초를 **추천 목록에서 뺀다** (재기는 한다) | **재는 방법을 정해야 한다** (아래) |

- **A 가 생기는 이유** : 에이전트는 앱이 뜬 시점부터 60초를 세고 **벽시계 분 경계에 맞춰 주지 않는다**. 전송이 조금씩 밀리다가 어느 순간 한 칸을 건너뛰면 그 칸은 비고 다음 칸에 2분치가 들어간다. GC 시간은 누적값이라(`#189`) 읽을 때 빼는데 그 뺄셈이 2분치가 된다
- **10초 간격이면 A 가 안 생긴다** : 1분 칸에 전송이 6번 들어와 하나가 밀려도 칸이 비지 않는다

### 2.6.2 정해야 하는 것 : 전송 간격을 재는 창이 60초면 짧다

`#36` 의 본 측정 창은 **60초**다. 그런데 전송 간격 후보가 10 · 30 · **60**초라 **창 안에 전송이 몇 번 드는지가 갈린다**.

전송 1번에 드는 CPU 를 `c` 라 한다. 창 안의 횟수는 **두 이웃한 값 중 하나**다.

**왜 딱 정해지지 않나** : 세 간격 모두 60초를 나누어 떨어뜨리므로 창이 **정확히** 60초면 `창 ÷ 간격` 으로 딱 정해진다. 그런데 **실제 창은 그보다 조금 길다** : 하네스 README 가 「측정 구간은 k6 컨테이너 기동 · 종료(1~3초, 부하 없음)를 포함한 약 60초」라고 적어 둔다. 그 1~3초가 회차마다 달라 전송이 한 번 더 들어올 수 있다.

| 전송 간격 | 창 60~63초 안의 횟수 | 그 회차의 전송 CPU | 회차 사이 흔들림 | 한 번 더 들어올 확률 |
|---|---|---|---|---|
| 10초 (지금) | 6번 또는 7번 | `6c` ~ `7c` | `c` (전송 비용의 약 17%) | **10 ~ 30%** |
| 30초 | 2번 또는 3번 | `2c` ~ `3c` | `c` (약 50%) | **3 ~ 10%** |
| 60초 | 1번 또는 2번 | `1c` ~ `2c` | `c` (**100%**) | **2 ~ 5%** |

- 확률은 **남는 시간 ÷ 간격**이다. 남는 시간이 1~3초라 바닥도 0 이 아니다 : 10초 간격은 `1÷10` ~ `3÷10` = 10~30% · 60초 간격은 `1÷60` ~ `3÷60` = 2~5%
- **10회를 돌리면 「한 번 더」가 몇 회 나오나** : 10초 간격 1~3회 · 30초 간격 0~1회 · 60초 간격 **0~1회**(기댓값 0.2~0.5)
- **그래서 흔들림이 생각보다 드물 수 있다** : 60초 간격에서 10회를 돌리면 열 번 다 1번으로 나올 수도 있다. 그러면 「두 무리」가 아니라 거의 한 무리다
- **이 확률을 우리는 아직 모른다** : 실제 창 길이도 실제 전송 간격(전송에 걸리는 시간만큼 설정값보다 길어진다)도 재 본 적이 없다. **`exports` 열이 그것을 처음 재는 것**이고 「문제 B 가 실제로 문제인가」도 그 열이 답한다
- **흔들림의 절대 크기는 세 경우 다 `c` 로 같다** : 창 안의 횟수가 **최대 1번 차이**나기 때문이다. 비율로 보면 간격이 길수록 커 보이는 것이다
- 그래서 **어느 두 설정을 비교하느냐에 따라 구분이 되고 안 되고가 갈린다**

| 비교 | 차이(신호) | 흔들림(잡음) | 구분되나 |
|---|---|---|---|
| 10초 대 60초 | `6c − 1c = 5c` | `c` | **된다** |
| 10초 대 30초 | `6c − 2c = 4c` | `c` | **된다** |
| 30초 대 60초 | `2c − 1c = c` | `c` | **안 된다** |

- 즉 「60초가 흔들린다」보다 정확한 문장은 **「30초와 60초를 창 60초에서 가르는 것은 불가능하다」** 다
- 그런데 **추천 후보는 10초와 30초**이고 60초는 재 두기만 하는 값이라, **꼭 가려야 하는 비교(10초 대 30초)는 창 60초에서도 된다**
- **고를 수 있는 길 셋** (5절에서 정한다)
  - ① 창을 60초로 두고 **회차를 늘려** 흔들림을 누른다 (`#36` 과 바로 비교된다)
  - ② 전송 간격 변형만 **창을 길게**(예 180초) 가져간다. 전송 횟수가 18 · 6 · 3 으로 정수가 되지만 **그 변형의 출발선도 같은 창으로 다시 재야** 한다
  - ③ 전송 CPU 만 따로 본다 : 부하 0 에서 간격만 바꿔 재면 전송 비용이 섞이지 않고 드러난다. 다만 운영 상황이 아니다
- **흔들림의 크기는 「창 ÷ 간격」에 달린다** : 창이 간격에 비해 짧을수록 커진다

| 창 | 간격 | 창 안의 전송 | 흔들림 |
|---|---|---|---|
| 60초 | 60초 | 1번 또는 2번 | **100%** |
| 180초 | 60초 | 3번 또는 4번 | 약 33% |
| 600초 | 60초 | 10번 또는 11번 | 약 10% |

- **적어 두는 것은 「보낸 횟수」가 아니라 「받은 건수」다** : 수집기 카운터(`monimo.collector.otlp.received`)는 **데이터 포인트 · 스팬 개수**를 센다(구현 2단계에서 코드로 확인했다). 그래서 CSV 열 이름도 `recv_metrics` · `recv_traces` 로 둔다
  - **건수에서 횟수를 얻는 길** : 한 번에 오는 건수를 `P` 라 하면 횟수는 `건수 ÷ P` 다. `P` 는 같은 변형의 회차들이 내는 값의 **차이**로 드러난다(예 414 와 708 이 섞여 나오면 `P` 는 294)
  - **그 차이가 전제 ① 의 시험이기도 하다** : `P` 가 간격마다 같아야 「전송 1번 비용이 간격과 무관하게 일정하다」가 선다
  - **건수를 적어 두면 `c` 를 구할 수 있다** : 회차들의 (횟수, CPU) 로 선을 그으면 기울기가 `c` 이고 y절편이 전송 말고 드는 것(적기 · 계측)이다
  - **이 카운터는 발신자를 안 가린다** : 쇼핑몰이 아닌 것이 같은 수집기로 보내면 섞인다. **뗌(off) 회차의 값이 그 배경값**이라 그 자체가 대조군이 된다
  - **이 환산이 서는 전제 셋은 5절 A 에 적었다** (`c` 가 간격과 무관하게 일정한지는 미확인 · 뗌 회차는 선에 넣지 않는다)

- **① 도 ② 도 흔들림을 0 으로 만들지는 못한다**
  - ① 은 흔들림을 **보이게** 하고 **전송 1번당 CPU 로 환산**한다 (회차마다 전송 횟수를 적으면 횟수가 수식에서 사라진다)
  - ② 는 100% 를 33% 로 **줄인다**
  - **「회차를 늘린 중앙값만으로는 안 풀린다」고 적었던 것을 내린다** : 그 말은 두 값이 **반반으로 갈린다**는 가정에서 나왔는데, 위 확률(10~30% · 3~10% · 2~5%)이면 **한쪽으로 크게 치우친다**. 치우치면 중앙값은 **흔한 쪽에 안정적으로 붙어** 오히려 믿을 만하다
  - 그래서 `exports` 열의 쓸모가 바뀐다 : **보정이 주된 목적이 아니라 「치우쳤는지」를 확인하는 것**이 주된 목적이다. 반반에 가깝게 나오면(= 남는 시간이 README 보다 크거나 전송이 설정값보다 많이 밀리면) 그때 보정이 필요해진다
  - **치우치면 `c` 를 선으로 구하기는 어려워진다** : 흔한 쪽에 점이 몰려 기울기가 안 선다. 그때는 되돌림 ② 의 ③(부하 0 에서 간격만)으로 간다
- 이 문제는 **측정 방법을 안 바꾼다는 1절의 경계에 닿는다** : 창을 바꾸면 `#36` 숫자와 바로 비교할 수 없게 되므로 바꿀지 말지는 결정 사항이다

### 2.7 자주 헷갈리는 것

- **「샘플링을 내려도 Service map 간선은 무조건 남는다」는 과한 말이다** : 간선은 **남은 표본으로** 그린다. 자주 쓰는 길은 1% 로도 거의 확실히 걸리지만 **드문 길은 표본에 안 들어와 사라진다**
- **「샘플링을 내리면 오버헤드가 준다」는 틀렸다** : 샘플링은 ② 단계고 계측 ① 은 그대로 돈다. `#36` 실측이 그걸 보였다. 샘플링이 줄이는 것은 ③ · ④ 와 **Collector 이후의 비용**이다
- **「메모리 100MB 가 힙이다」는 틀렸다** : 절반은 클래스 · JIT 쪽이라 힙 설정이나 샘플링으로 안 준다
- **「배치를 키우면 가벼워진다」는 반만 맞다** : 전송 횟수는 줄지만 큐에 더 쌓여 메모리가 늘고 화면이 늦어진다. **CPU 와 메모리가 반대로 가는 유일한 설정**이다
- **상대 증가율과 %p 는 다른 말이다** : 가벼운 앱일수록 상대 증가율이 부풀어 같은 측정으로 통과도 실패도 쓸 수 있다. `#36` 과 ADR `#56` 이 **1코어 대비 %p** 로 판정 기준을 고정해 뒀으니 이번에도 그 기준을 쓴다
- **`metrics-off` · `instr-min` 은 운영 설정이 아니다** : 끄면 화면의 메트릭이 빈다. 이번 이슈의 목적은 **끄는 것이 아니라 줄이는 값**을 찾는 것이다

## 3. 1차 질문 (사람 차례)

승조가 2절을 읽고 물은 것이다. **원문 그대로 둔다** (맞춤법 · 띄어쓰기도 고치지 않는다).
답은 바로 아래에 붙이고, 그 질문으로 **문서가 바뀐 것**은 「고친 것」으로 표시한다.

**Q1.**

```
2.4 이번에 측정하지 않는 목록인데 왜 해당 부분은 측정하지 않는 거지?
```

- A. 여섯 줄이 셋 · 셋으로 갈린다
  - **그대로 쓰는 셋** : 출발선 둘(뗌 · 지금 설정)과 메모리 바닥 45~55MB. 조건이 같으면 같은 값이 나오고, 바닥은 어떤 설정도 안 건드린다. 다시 재면 2시간 40분이 더 들고 결론은 안 바뀐다
  - **모양을 바꿔 다시 재는 셋** : 샘플링(10% → 1% 까지 · 메모리도), 쓰는 계측만 켜기(회차를 늘려 CPU 도 판정), 메트릭(끄기 대신 **간격**으로. 끄기는 운영에 쓸 수 없는 설정이다)
  - 정확히 말하면 출발선은 **매 회차 다시 재어진다** : 하네스가 붙임 · 뗌을 번갈아 돌린다. 2.4 의 뜻은 「안 잰다」가 아니라 **「그 숫자를 새 발견으로 다시 조사하지 않는다」** 다
  - **고친 것** : 소제목이 「다시 재지 않는 것」이라 과하게 읽혔다

**Q2.**

```
비교의 출발선이다. 손잡이를 돌린 값과 빼기를 해야 하니 출발선이 필요한 것이고, 조건이 같으면 같은 값이 나온다 라는 말 설명해줘
```

- A. 에이전트 비용은 절대값으로 못 재고 **빼기**로 낸다
  - `에이전트 비용 = (붙이고 쓴 CPU) − (떼고 쓴 CPU)`
  - 이번에 낼 숫자는 「설정을 바꾸면 **출발선에서 얼마나 내려가나**」다. 예로 계측을 줄여 +2.0%p 가 나오면 출발선 +3.6%p 에서 1.6%p 내려간 것이다
  - 출발선이 없으면 「+2.0%p」가 좋은지 나쁜지 말할 수 없다
  - 「조건이 같으면」은 같은 맥북 · 같은 제한(CPU 1개 · 메모리 1GB) · 같은 부하 · 같은 창(워밍업 40초 + 60초)을 뜻한다
  - 번갈아 돈 출발선이 `#36` 값과 **많이 다르게 나오면 그 자체로 알려야 하는 사실**이다

**Q3.**

```
메트릭 간격 60초에서 그래서 30초까지만 권고 후보라는 것이 뭘 말하는 거지?
```

```
60초 세면 값이 밀릴 수 있으니까 60초마다의 컴퓨팅 자원은 패스 하자는 거고
```

- A. **60초도 잰다. 추천만 안 한다**
  - 재는 값 : 10초 · 30초 · 60초
  - 추천할 값 : 10초 또는 30초 (60초는 `#238` 로 사고 이력이 있고 `PR #224` 리뷰에서 「운영은 10~30초」를 약속했다)
  - 60초를 재는 이유 : 「30초를 고르면서 **CPU 몇 %p 를 포기했는지**」를 숫자로 말하려고. 재 두지 않으면 「위험해서 안 썼다」만 남고 얼마를 포기했는지 모른다

**Q4.**

```
각 손잡이의 대가가 뭔 말? 손잡이는 뭔말?
```

```
손잡이 대가 같은 비유표현을 일반적인 표현으로 수정해줘
```

- A. 비유였다. 손잡이 = **우리가 값을 바꿀 수 있는 설정**, 대가 = **줄인 대신 내주는 것**
  - **고친 것** : 문서와 이슈 본문에서 「손잡이 → 조절할 설정」 · 「대가 → 잃는 것」으로 바꿨다. 나중에 면접에서 보여 줄 문서라 비유 없는 말로 둔다

**Q5.**

```
계측을 줄이면 안 쓰는 줄만 지워야 한다는 무슨 말인지 쉽게 설명해줘
```

```
계측은 에이전트가 우리 서비스가 흘러가는 모든 흐름을 다 보고 측정하는 건데 측정할 때 JDBC나 Redis 처럼 필수적인 부분은 끄지 않고 계측한다는 건가? 필수 부분을 빠뜨리면 다른 측정해야하는 부분이 사라지니까
```

- A. 맞다. 그리고 한 가지만 좁히면 된다
  - 에이전트는 「모든 흐름」을 보는 것이 아니라 **자기가 아는 라이브러리**만 본다. 수백 개용 계측을 들고 있고 그게 **기본으로 다 켜져** 있다. 쇼핑몰이 쓰는 것은 여섯 개쯤이다
  - 그래서 **전부 끄고 쓰는 것만 켠다**
  - 켜는 목록에서 하나를 빠뜨리면 **그 구간이 트레이스에서 사라진다** : JDBC 를 빠뜨리면 DB 구간이 없어져 느린 쿼리를 못 찾고, Redis 를 빠뜨리면 캐시 히트 · 미스 구간이 사라진다
  - 즉 **공짜로 줄이는 것과 화면을 망가뜨리는 것이 목록 한 줄 차이**다. 그래서 끈 뒤 ClickHouse `spans` 로 눈으로 확인한다
  - 「필수」의 판단 기준 한 줄 : **그 구간이 화면이나 트레이스에 보여야 하나**
  - **고친 것** : 2.5 의 제목이 「안 쓰는 줄만 지워야 한다」로 애매했다 → 「쓰는 것을 끄면 트레이스에 구멍이 난다」

**Q6.**

```
배치를 키우면 잃는 것은 신선도다라는 건 배치를 키울 때마다 한 번 가는 간격이 늘어나서 신선도가 떨어진다는 건가?
```

- A. 맞다. 한 줄만 보탠다
  - 배치는 **두 조건 중 먼저 오는 것**으로 보낸다 : 묶음이 찼을 때 · 주기가 됐을 때. 그래서 늦어지는 길이 둘이다
  - 지금 요청 → 화면까지 중앙 2.65초 · p95 5.1초이고 **그 대부분이 이미 이 기다림**이다
  - 보탤 한 줄 : **큐를 키우면 메모리가 늘 수 있다** → CPU 와 메모리가 반대로 가는 유일한 설정이다

**Q7.**

```
설정마다 무엇을 잃나부분은 해당 설정에 따라 조절했을 때 어떻게 되는 지를 보여주는 거라고 이해하면 되는 건가?
```

- A. 거의 맞다. 그중 **나빠지는 쪽만** 모은 절이다
  - **좋아지는 쪽**(CPU %p · 메모리 MB)은 **측정하면 숫자로 나온다**
  - **나빠지는 쪽**(지표 해상도 · 드문 경로 · 트레이스 구멍 · 신선도)은 **측정으로 안 나오니 미리 적어 둔다**
  - 적어 두는 이유 : 「CPU 가 1.2%p 줄었다」만 있으면 운영에 넣자고 추천할 수 없다. 추천이 되려면 **「이만큼 줄고 이만큼 잃는다」** 두 쪽이 다 필요하다

**Q8.**

```
60초 이슈는 에이전트가 collecter로 전송할 때 우리가 60초 동안 CPU 상태를 재는 건가?
```

- A. 아니다. **60초가 두 가지 뜻으로 쓰여서** 헷갈린 것이다
  - **본 측정 60초** : 우리가 CPU 를 재는 창. **설정과 무관하게 늘 60초**다
  - **전송 간격 60초** : 에이전트가 지표를 보내는 주기. **설정값**이다
  - **고친 것** : 이 질문이 진짜 문제를 찾았다. 창 60초와 간격 60초가 겹치면 **창 안에 전송이 1번 들어올지 2번일지가 운에 달린다** → 2.6.1 · 2.6.2 로 적고 선택지 셋을 올렸다

**Q9.**

```
샘플링은 일단 collector 에서 진행하는 거였고 서비스맵 간선은 샘플링해도 사라지지 않고 (무조건 어디에서 어디로 가는 지는 무조건 남으니까) CPU 도 샘플링한다고 해서 스팬들을 조립할 때 CPU 일이 줄어드는 것이 아니니까 CPU를 측정한다는 건가?
```

- A. 두 군데를 바로잡아야 한다
  - **샘플링이 두 층에 있다** : 앱 쪽(`otel.traces.sampler`, 지금 `always_on`)과 Collector 쪽(`application_configs.sampling_rate`, `#121` · `#206`). 네가 기억한 「Collector 에서」는 `#206` 에서 한 그 샘플링이고, **이번에 바꾸는 것은 앱 쪽**이다
  - **간선이 「무조건」 남는 것은 아니다** : 간선은 남은 표본으로 그린다. 자주 쓰는 길은 1% 로도 거의 확실히 걸리지만 **드문 길은 사라진다**
  - CPU 를 재는 목적은 맞게 봤다 : 「줄겠지」를 확인하려는 것이 아니라 **「안 준다」를 숫자로 못박으려고** 잰다. 그러면 나중에 「CPU 가 높으니 샘플링 내리자」에 숫자로 답할 수 있다
  - **고친 것** : 두 층 구분과 간선 정정을 2.2 · 2.7 에 넣었다

**Q10.**

```
1번으로 했을 때 문제가 생기는 부분은 없는 건가?
```

- A. 셋 있고 **그중 하나는 회차를 늘려도 안 풀린다**
  - **문제 1** : 재려는 차이가 흔들림보다 작을 수 있다. 전송만 아끼는 몫은 0.1~0.3%p 수준으로 보이는데 `#36` 은 같은 크기의 효과를 「흔들림에 묻혀 단정 못 했다」고 적었다
  - **문제 2 (가장 중요)** : 1번 대 2번은 **흔들림이 아니라 편향일 수 있다**. 전송 시각은 JVM 이 뜬 순간부터 세고 우리 창은 고정된 시간 뒤에 열린다. 위상이 고정돼 있으면 **매 회차 같은 횟수가 들어와 아주 안정적으로 틀린 값**이 된다. 회차를 100번 늘려도 똑같다
  - **문제 3** : 시간과 드리프트. 회차가 늘면 MySQL 주문 표가 쌓여 뒤 회차 쿼리가 무거워지고 맥북 발열도 쌓인다. 중간발표가 10/31 이라 시간이 넉넉하지 않다
  - **고친 것** : 문제 2 는 고칠 수 있다 → **수집기가 받은 건수를 회차마다 기록한다**(`monimo.collector.otlp.received`). 그러면 흔들림인지 편향인지 보이고, 전송 1번당 CPU 를 낼 수 있고, 어긋난 회차를 버릴 수 있다. 2.6.2 선택지 ① 에 붙였다. **그 카운터가 「횟수」가 아니라 「건수」라는 것은 구현 2단계에서 코드를 읽어 알았다**(2.6.2)

## 5. 선택지와 설명

### 조사 프롬프트

- 원문은 같은 폴더의 [`prompts.md`](prompts.md) 에 둔다
- 4절 「아직 모르는 것」 다섯과 5절 묶음(A~E)은 **1대1이 아니다**
  - A ← 전송 간격을 어느 창에서 재나 · B ← 배치를 얼마나 키워 볼지 · C ← 권고값 부하 기준 · D ← 계측 목록을 더 줄일지
  - 4절의 「배치 기본값의 실제 숫자」는 **고를 것이 아니라 확인할 것**이라 B 의 머리글에 두고 7절 구현 1단계로 보냈다
  - **E(회차 수)는 4절에 없던 것**이다 : A 를 ① 로 고르면 회차 수를 정해야 해서 **따라온 결정**이다
- 1절 「알고 싶었던 것」 번호는 답하는 소제목 괄호에 달았다 : ① 은 D · ② 는 A · ③ 은 B · ⑤ 는 C
- **④(설정마다 무엇을 잃나)는 5절에 선택지가 없다** : 고를 것이 아니라 **이미 아는 것**이라 2.5 에 적혀 있고, 측정 뒤 확인 계획은 7절 「잃는 것 확인」에 둔다

### A. 전송 간격을 어느 창에서 재나 (알고 싶었던 것 ②)

전송 1번에 드는 CPU 를 `c` 라 한다. 창 안의 전송 횟수는 세 간격 모두 **두 이웃한 값 중 하나**이고 흔들림의 절대 크기는 셋 다 `c` 다 (2.6.2).

**① 의 환산이 서는 전제 셋** (여기가 ① 을 고르는 자리라 2.6.2 에서 옮겨 적는다)

- ① **전송 1번 비용 `c` 가 간격과 무관하게 일정하다** : 보내는 것이 그 시점의 전 시계열 스냅샷이라 간격이 길어도 양이 비슷하다는 가정이고 **미확인**이다. 깨지면 선이 휘어 기울기가 하나로 안 나오고, 그때는 간격별로 따로 본다
- ② **전송 말고 드는 CPU 가 간격 설정에 안 흔들린다** : 요청마다 적는 일은 간격과 무관하다는 것이고 2.1 의 「지표 두 종류」가 근거다. 다만 **내보낼 때 읽는 게이지**는 간격에 따라 줄어서 그 몫이 `c` 에 섞여 들어간다(분리하지 않는다)
- ③ **뗌 회차는 선에 넣지 않는다** : 뗌의 `(0회, CPU)` 는 「에이전트는 붙었는데 전송만 0번」이 아니라 계측 · 샘플링 · 전송이 **다 없는** 상태다. 같은 선 위에 없으므로 넣으면 기울기가 끌려간다. 뗌은 **빼기의 기준선으로만** 쓴다

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **① 창 60초 유지 + 회차 늘리기 + 전송 횟수 기록 (고를 안)** | `#36` 숫자와 **바로 비교된다**. 하네스에 두 줄(회차 앞뒤로 수집기 카운터 읽기)이면 된다. **횟수가 치우쳤는지를 처음 재는 것**이고, 섞여 나오면 `c` 를 선으로 구해 횟수 차이를 수식에서 지울 수도 있다 | 흔들림을 **0 으로 만들지는 못한다**. `30초 대 60초`(차이 `c` · 잡음 `c`)는 **끝내 못 가린다**. 그리고 **2.6.2 확률대로 치우치면 `c` 를 선으로 구하는 것은 안 된다**(흔한 쪽에 점이 몰려 기울기가 안 선다) : 그때는 되돌림 ② 로 ③(부하 0)으로 간다 |
| ② 전송 간격 변형만 창을 180초로 | 흔들림이 100% → 33% 로 준다. 전송 횟수가 3 · 6 · 18 로 커져 비율이 안정된다 | **그 변형의 출발선(뗌 · 지금 설정)도 같은 창으로 다시 재야** 한다. 1절이 못박은 「측정 방법은 안 바꾼다」를 깬다. 회차 시간도 1.5배가 된다 |
| ③ 부하 0 에서 간격만 바꿔 잰다 | 적기 비용이 거의 없어 **전송 비용만 깨끗하게** 남는다. 부하가 없으니 창을 아주 길게(10분) 잡아도 싸다 | **운영 상황이 아니다**. 요청이 있을 때의 전송 비용(큐 경합 · GC 영향)을 못 본다. 권고값의 근거로 쓰기엔 약하다 |
| ④ 안 잰다 (지금 10초를 그대로 쓴다) | 시간 0 | `#36` 이 「메트릭이 CPU 증가의 약 1/5」로 **짚어 둔 가장 큰 후보를 안 건드린다**. 운영 간격을 고를 근거가 안 생긴다 |

- **꼭 가려야 하는 비교는 `10초 대 30초`** 다 : 추천 후보가 그 둘이고 차이가 `4c` 라 **창 60초에서도 가려진다**
- 60초는 `#238`(1분 칸이 비거나 2분치가 몰린다) 때문에 **추천 후보가 아니다**. 재 두는 것은 「30초를 고르며 몇 %p 를 포기했나」를 적기 위한 것이다
- ① 과 ② 는 **같이 쓸 수 있다**. 다만 ② 의 값을 치를 이유가 생기는 것은 **횟수가 회차마다 고정으로 나올 때**다 (그때는 회차를 늘려도 안 풀린다)

### B. 배치를 얼마나 키워 볼지 (알고 싶었던 것 ③)

**기본값의 실제 숫자가 아직 미확인**이다. 문서 기준으로는 큐 2048 · 묶음 512 · 주기 5초로 알고 있으나 에이전트 2.31.1 에서 그 값인지는 확인하지 않았다.

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **① 기본값을 먼저 확인하고 묶음과 주기를 각각 2배 (고를 안)** | 한 번에 **한 가지만** 바꿔 CPU 와 메모리가 어느 쪽에서 움직이는지 가른다. 2배는 되돌리기 쉽고 신선도 영향도 예측 범위다 | 회차가 둘 늘어난다(묶음 2배 · 주기 2배). 더 크게 키웠을 때의 한계는 안 보인다 |
| ② 묶음 · 큐 · 주기를 한꺼번에 크게 | 회차가 하나로 끝나고 효과가 가장 크게 보인다 | **무엇이 효과를 냈는지 모른다**. CPU 와 메모리가 반대로 가는 설정이라 섞으면 해석이 막힌다 |
| ③ 큐만 키운다 | 메모리 쪽 변화를 가장 선명하게 본다 | **CPU 는 거의 안 변한다**(큐 크기는 전송 횟수를 안 바꾼다). 재는 목적의 절반이 빠진다 |
| ④ 안 잰다 | 시간 0 | 네 설정 중 **한 번도 건드린 적 없는 유일한 것**을 계속 모르고 둔다. 운영에서 기본값이 맞는지도 모른다 |

- 큐와 묶음은 역할이 다르다 : **묶음**은 한 번에 보내는 개수(전송 횟수를 바꾼다) · **큐**는 기다릴 수 있는 총량(메모리와 버림 여부를 바꾼다)
- 그래서 **CPU 를 보려면 묶음과 주기**, **메모리를 보려면 큐**다

### C. 권고값을 어떤 부하 기준으로 낼지 (알고 싶었던 것 ⑤)

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| **① 초당 20건으로 판정하고 40건으로 버티는지 본다 (고를 안)** | ADR `#56` 판정 기준(20건)과 **그대로 이어진다**. 40건은 `#36` 이 「CPU 가 넘는다」로 남긴 자리라 **권고값이 그걸 되돌리는지**가 바로 보인다 | 회차가 2배다. 10건(여유 있는 쪽)은 안 본다 |
| ② 초당 20건만 | 가장 빠르다 (`#36` 기록으로 부하 하나는 약 35분) | **부하 비례를 못 본다**. `#36` 이 같은 이유로 버린 선택지다 |

- 운영 예상은 **초당 주문 20건**이다 (backend `20-scope.md` 역산)
- 그래서 **20건으로 고르고 40건으로 검산**하는 것이 지금 기준과 가장 잘 맞는다

### D. 계측 목록을 더 줄일지 (알고 싶었던 것 ①)

| 방법 | 얻는 것 | 포기하는 것 |

| **① `#36` 의 `instr-min` 목록을 그대로 쓰고 회차만 늘린다 (고를 안)** | `#36` 이 **ClickHouse `spans` 로 화면이 그대로인지 이미 확인해 둔 목록**이다. 그래서 **CPU 판정만 추가하면 끝난다**(그 이슈가 못 낸 숫자다) | 더 줄였을 때의 여지를 안 본다 |

- 그래서 ① 로 두고 **더 줄이는 것은 후속**으로 남긴다

### E. 회차를 몇 번으로 할지 (A 를 ① 로 고른 데서 따라오는 결정)

| 방법 | 얻는 것 | 포기하는 것 |
|---|---|---|
| ① 5회 (`#36` 과 동일) | 시간이 가장 적다 | `#36` 이 **같은 크기의 효과를 「흔들림에 묻혀 단정 못 했다」** 고 적은 회차 수다. 그걸 반복할 위험이 있다 |
| **② 10회 (고를 안)** | `#36` 의 **원인 찾기 실험**이 못 단정한 것을 이번에 단정하려는 것이다. 그 실험은 **3회 · 번갈아 안 돌림 · 30분 뒤 이어 돌림**이었고 `instr-min` 9% 는 「흔들림과 구분 안 됨」, 메트릭 끄기 22% 는 「범위 일부 겹침」으로 남았다. **약점 셋을 다 고친다** : 회차 3 → 10 · 번갈아 · 같은 시간대 | 부하 하나 · 설정 넷에 약 2시간이 든다 |
| ③ 15회 이상 | 선이 더 안정된다 | 시간이 3배가 되고 **MySQL 주문 표가 쌓여 뒤 회차가 무거워지는** 영향이 커진다. 중간발표(10/31) 전이라 시간이 빡빡하다 |

- 회차를 늘리는 이유는 **기계 잡음에서 중앙값을 좁히는 것**이다
- **`#36` 의 5회가 모자랐던 것이 아니다** : 그 이슈의 **본 실험**(붙임 대 뗌, 5회 번갈아)은 **통했다**. 12칸 중 11칸에서 「붙임 최솟값 > 뗌 최댓값」이 나왔다
- 못 단정한 것은 **원인 찾기 실험**이고 약점이 셋이었다 : **3회뿐** · **번갈아 안 돌림** · **30분 뒤 이어 돌림**. 그래서 회차별 범위가 겹쳤다(on 19.0~20.8ms · metrics-off 18.7~19.6ms · instr-min 19.3~20.3ms)
- **이번에 재려는 것이 바로 그 크기**다(`instr-min` 9% · 메트릭 끄기 22%). 그래서 그 약점 셋을 다 고친다
- **처음에는 「전송 1번 무리 · 2번 무리를 각각 5개씩 모으려고」로 적었는데 그 근거는 내렸다** : 2.6.2 의 확률(2~30%)이면 두 무리가 반반이 아니라 한쪽으로 치우친다. 10회를 돌려도 **흔한 쪽이 7~10회**다. 치우친 것 자체가 **쓸 만한 발견**(문제 B 가 작다)이지만 「5개씩」은 안 된다
- 홀수여야 중앙값이 하나로 정해지지만, 이번에는 **중앙값만 보지 않고 횟수로 갈라 보기 때문에** 짝수여도 된다
- **이것도 1절의 경계를 건드린다** : 1절 「건드리지 않는 것」에 측정 방법으로 **「5회 번갈아 중앙값」**이 적혀 있다. A 의 창 크기와 같은 성격의 잠금이다
  - 그런데 **창을 바꾸는 것과 회차를 늘리는 것은 값이 다르다** : 창을 바꾸면 `#36` 숫자와 **비교 자체가 안 되고**(출발선을 다시 재야 한다), 회차를 늘리는 것은 **같은 조건에서 표본을 더 모으는 것**이라 `#36` 숫자와 그대로 비교된다
  - 그래서 창은 안 바꾸고 회차만 늘린다. **잠금을 건드린 것은 사실이므로 여기 적어 둔다**

## 6. 2차 질문 (사람 차례)

**순서를 밝혀 둔다** : 아래 질문들은 5절을 **읽고 나서가 아니라 5절을 쓰는 동안** 나왔다. 틀의 순서(5 → 6)와 다르지만 내용은 5절 A 와 E 를 정하는 질문이라 여기에 둔다. 원문 그대로 둔다.

**Q1.**

```
CPU 가 튄다는 건 해당 시간에 CPU 사용량이 안보인다는 소리?
```

- A. 아니다. **안 보이는 것이 아니라 회차마다 숫자가 달라지는 것**이다
  - 한 회차마다 「그 60초 동안 CPU 를 몇 초 썼나」가 **늘 나온다**. 빈칸이 되는 일은 없다
  - 전송이 2번 들어온 회차는 1번 들어온 회차보다 **전송 1번 비용만큼 크다** → 두 무리로 갈린다
  - 문제 A 와 갈리는 자리다 : **A 는 값이 없고(칸이 빈다) B 는 값이 흔들린다**

**Q2.**

```
문제 B도 30,10 초면 CPU 안튀나?
```

- A. **셋 다 튄다. 내가 전에 적은 표가 틀렸다**
  - 「30초 → 2번」으로 딱 정해진 것처럼 적었는데 실제로는 **2번 또는 3번**이다
  - 창 안의 횟수는 세 간격 모두 **두 이웃한 값 중 하나**이고 **흔들림의 절대 크기는 셋 다 `c`**(전송 1번 비용)다. 비율로 보니 간격이 길수록 커 보이는 것이다
  - 그래서 정확한 문장은 「60초가 흔들린다」가 아니라 **「`30초 대 60초`를 창 60초에서 가르는 것은 불가능하다」**(차이 `c` · 잡음 `c`)다
  - 다행히 **꼭 가려야 하는 비교는 `10초 대 30초`**(차이 `4c`)이고 그것은 창 60초에서도 가려진다
  - **고친 것** : 2.6.2 의 표를 세 간격 다 「두 이웃한 값 중 하나」로 정정하고 신호 대 잡음 표를 더했다
  - **그 뒤 한 번 더 고쳤다** : 중간에 「`창 ÷ 간격` ±1」로 적어 60초에서 0번이 나올 수 있다고 썼는데 **틀렸다**. 세 간격이 다 60초를 나누어 떨어뜨리므로 값은 늘 **두 이웃한 값**이고, 한 번 더 들어오는 것은 **창이 60초보다 1~3초 긴 것**(k6 기동 · 종료 포함) 때문이다. 그 확률이 **남는 시간 ÷ 간격**이라 60초 간격에서는 최대 5% 이고, 그래서 **문제 B 가 생각보다 작을 수 있다**는 것까지 적었다

**Q3.**

```
왜 각 ㅂ5회차씩이지?
```

- A. 통계 공식이 아니라 **실측 + 홀수 + 시간 예산**에서 나왔다
  - `#36` 파일럿에서 **뗌 회차 하나가 p95 25ms · CPU +20% 로 튀었다**. 그 기록의 결론이 「판정에는 5회 이상 번갈아 중앙값이 필요하다」다
  - **홀수**여야 중앙값이 하나로 정해진다. 짝수면 가운데 둘의 평균이라 튄 값이 섞인다
  - **시간** : 부하 셋 × 붙임 뗌 × 5회가 약 1시간 45분이었다. 부하 하나만 5회면 35분인데 부하 비례를 못 봐서 버렸다
  - 5 가 충분하다는 뜻은 아니다 : `#36` 은 **「12칸 중 11칸에서 붙임 최솟값 > 뗌 최댓값」**(두 무리가 안 겹친다)으로 따로 못박았고, 겹치는 경우는 **단정하지 않았다**

**Q4.**

```
1번으로 했을 때 문제가 생기는 부분은 없는 건가?
```

- A. 셋 있고 **그중 하나는 회차를 늘려도 안 풀린다**
  - **문제 1** : 재려는 차이가 흔들림보다 작을 수 있다. `#36` 은 같은 크기의 효과를 「흔들림에 묻혀 단정 못 했다」고 적었다
  - **문제 2** : 1번 대 2번은 흔들림이 아니라 **편향일 수 있다**. 전송 시각은 JVM 이 뜬 순간부터 세고 우리 창은 고정된 시간 뒤에 열리므로, 위상이 고정되면 **매 회차 같은 횟수가 들어와 안정적으로 틀린 값**이 된다. 회차를 100번 늘려도 같다
  - **문제 3** : 시간과 드리프트. MySQL 주문 표가 쌓여 뒤 회차가 무거워지고 맥북 발열도 쌓인다. 중간발표(10/31)가 가깝다
  - **문제 2 는 고칠 수 있다** → 전송 횟수를 회차마다 기록하면 흔들림인지 편향인지 보이고 `c` 를 직접 구할 수 있다. 그래서 ① 은 **「회차 늘리기 + 횟수 기록」이 한 묶음**이다

**Q5.**

```
1번이 횟수를 늘리게 되면서 가끔씩 많이 늘어난 부분을 중앙값으로 대체해서 측정한다는 거지?
```

- A. 반만 맞다
  - **맞는 쪽** : 어쩌다 한 번 크게 튄 회차(맥북이 딴 일을 한 경우)는 중앙값이 걸러 준다. `#36` 이 평균 대신 중앙값을 쓴 이유다
  - **안 맞는 쪽** : 1번 대 2번은 「튄 값」이 아니라 **반반으로 갈린 두 정상 값**이다. 중앙값은 **더 많이 나온 쪽으로 붙는다**
  - 그래서 ① 의 핵심은 중앙값이 아니라 **횟수 기록**이다. 횟수를 알면 갈라 보거나 나눠서 환산하거나 어긋난 회차를 버릴 수 있다
  - **이 답의 「반반」이 틀렸다 (나중에 2.6.2 를 다시 계산하며 드러났다)** : 한 번 더 들어올 확률이 **남는 시간 ÷ 간격**이라 2~30% 다. 반반이 아니라 **한쪽으로 크게 치우친다**. 치우치면 중앙값은 흔한 쪽에 안정적으로 붙어 **오히려 믿을 만하다**
  - 그래서 결론이 바뀌었다 : 횟수를 기록하는 주된 이유가 **보정**이 아니라 **「치우쳤는지 확인」**이다. 반반에 가깝게 나오면 그때 보정이 필요해진다. 틀린 답을 지우지 않고 남겨 둔다

### 결정 원문

```
5절 써주고 방법은 회차 늘리기로 하고 6절7절8절 전부 작성해줘
```

- **승조가 실제로 말한 것은 한 가지다** : 「**회차 늘리기**」. 5절 A 의 세 묶음 중 그 하나를 고른 것이다
- **내가 보태서 7절에 적은 것 둘** : A① 의 나머지 두 조각인 **창 60초 유지**와 **전송 횟수 기록** · 그리고 **회차를 몇 번으로 할지(10회)**
  - 창 60초 유지는 「회차 늘리기」를 고른 데서 거의 따라온다(창을 바꾸는 것이 ② 였다)
  - **전송 횟수 기록과 10회는 따라오지 않는다** : 6절 Q4 · Q5 의 답에서 내가 「횟수 기록 없는 ① 은 반쪽이다」로 제안한 것이고 승조가 명시로 고른 것이 아니다. 아니면 7절 표를 고치면 된다

### 잃는 것 확인 (숫자와 따로 한다)

- `instr-min` · 샘플링 1% 회차 뒤에 **ClickHouse `spans` 를 뒤져** 스팬 모양과 Service map 간선이 `#36` 때와 같은지 본다
- 샘플링 1% 는 **드문 경로가 사라지는 것이 정상**이다. 「간선 수가 줄었다」가 아니라 **「어떤 간선이 사라졌나」**를 적는다
- 배치 변형은 **요청 → 화면 지연**을 같이 재서 적는다 (지금 중앙 2.65초 · p95 5.1초)

### 건드리지 않는 것

- 운영 설정 (`otel/agent.properties` · `docker-compose.dev.yml`) : 권고값은 문서로만 낸다
- 측정 방법 : cgroup 읽기 · CPU 1개 메모리 1GB 제한 · 워밍업 40초 · 본 측정 60초 · 뗌은 `-javaagent` 를 아예 빼기
- Collector 쪽 샘플링 비율 (`application_configs.sampling_rate`) : 앱 부담과 무관하고 배포 5~7단계 몫이다
- 요구사항 문장 (ADR `#56`) : 권고값이 그 기준을 만족시키는지만 적는다
- `#36` 의 `results.csv` · `results.md` : 새 파일에 쌓고 그 기록은 그대로 둔다

### 확인 방법 (끝났다고 말할 근거)

- 설정 여섯 변형에 **CPU %p · 상대 증가율 · 주문 1건당 ms · 메모리 MB** 가 중앙값으로 나왔다
- CSV 에 `exports` 열이 있고, 전송 간격 묶음에서 **횟수가 회차마다 섞였는지 고정인지** 말할 수 있다
- **전송 1번당 `c`** 를 숫자로 냈거나, 못 냈으면 **왜 못 냈는지**(흔들림에 묻혔다)를 적었다
- `10초 대 30초` 를 **가렸거나 못 가렸다고 말할 수 있다**
- `instr-min` · 샘플링 1% 의 ClickHouse 확인 결과가 적혀 있다
- 권고값 한 벌이 있고, 각 값마다 **얼마 줄고 무엇을 잃는지** 한 줄씩 있다
- ADR `#56` 기준(1코어 +3%p · 메모리 150MB)을 초당 20건에서 만족하는지, 40건에서는 어떤지 적혀 있다

### 되돌림 다섯

- ① **전송 횟수가 회차마다 고정으로 나오면** 5절 A② 로 올라간다(창 180초). 그때는 그 변형의 출발선도 같은 창으로 다시 잰다
- ② **전송 1번당 `c` 가 흔들림에 묻히면** 5절 A③ 으로 내려간다(부하 0 에서 간격만). 운영 상황이 아니라는 한계를 같이 적는다
- ③ **배치 2배가 메모리를 크게 늘리면**(예 +20MB 넘게) 묶음만 키우고 큐는 기본값으로 둔다. 큐는 전송 횟수를 안 바꾸므로 CPU 에 기여가 없다
- ④ **에이전트를 3.0 으로 올리면** 기본값이 바뀔 수 있으므로 1단계(기본값 확인)부터 다시 돈다
- ⑤ **운영 실측 부하가 초당 40건을 넘으면** 5절 C 의 판정 기준을 올려 다시 잰다

### 여기서 나온 면접 질문

1. 측정 창과 데이터 전송 주기가 같은 길이면 무슨 일이 생기나 (답 : 창 안에 들어오는 전송이 1번 또는 2번으로 갈려 측정값이 전송 1번 비용만큼 흔들린다. 흔들림의 절대 크기는 간격과 무관하게 전송 1번 비용이고 비율만 달라진다)
2. 그 흔들림을 회차를 늘린 중앙값으로 누를 수 있는지는 무엇에 달려 있나 (답 : 두 값이 반반으로 갈리면 못 누른다. 중앙값이 많이 나온 쪽으로 붙어 그 쪽 값이 운에 달린다. 그런데 한쪽으로 치우치면 중앙값은 안정적이라 누를 수 있다. 어느 쪽인지는 추측이 아니라 전송 횟수를 기록해 봐야 안다. 우리 경우 확률은 「남는 시간 ÷ 간격」으로 2~30% 라 치우치는 쪽으로 예상된다)
3. 트레이스 샘플링을 내리면 앱의 CPU 가 줄지 않는 이유는 무엇인가 (답 : 계측이 샘플링 결정보다 먼저 돌아 스팬을 이미 만든다. 샘플링이 줄이는 것은 큐 · 전송과 수집기 이후다)
4. 지표 전송 간격을 늘리면 무엇이 줄고 무엇이 그대로인가 (답 : 보내기와 내보낼 때 읽는 게이지는 줄고, 요청마다 히스토그램 칸에 적는 일은 그대로다. 그래서 간격을 늘려도 CPU 가 거의 안 줄 수 있다)
5. 같은 설정 변경이 운영과 측정에서 각각 다른 사고를 일으킨 예를 들라 (답 : 전송 간격 60초. 운영에서는 저장소 1분 칸과 같아져 칸이 비거나 2분치가 몰리고, 측정에서는 60초 창과 같아져 숫자가 흔들린다. 둘 다 「주기가 칸 길이와 같으면 경계에서 터진다」의 사례다)

원문 그대로 둔다. **원문이 고른 것은 「회차 늘리기」 한 가지**이고, 여기에 없어서 내가 보탠 것은 다섯이다.

- **전송 횟수를 수집기에서 읽는 것** : 횟수 기록 없는 ① 은 흔들림인지 편향인지 못 가린다 (6절 Q4)
- **회차를 10회로 정한 것** : 「늘리기」만 말했고 수는 안 말했다. `#36` 의 원인 찾기 실험이 **3회 · 번갈아 안 돌림**으로 못 단정한 크기라 그 2배 넘게 두고 번갈아 돌린다
- **10회를 전송 간격 묶음에만 적용한 것** : (변형, 부하) 쌍 열둘을 전부 10회로 하면 120 회차 약 7시간 20분이다
- **배치 기본값 확인을 1단계로 둔 것** : 아직 미확인이라 「2배」의 기준이 없다
- **잃는 것 확인을 숫자와 따로 둔 것** : 숫자가 좋아졌는데 화면이 비면 개선이 아니다
