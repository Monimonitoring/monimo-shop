# `#51` 오버헤드를 줄이는 설정 넷 측정 결과

- 측정 2026-10-27 / 승조(`@SeungJo-02`) / 방법 [`perf/overhead/`](../../../perf/overhead/README.md) / 원자료 [`results.csv`](results.csv) (회차 × 서비스 340줄)
- 대상 : 쇼핑몰 네 서비스(gateway · order · payment · inventory), OTel Java Agent 2.31.1 + 스레드 덤프 Extension. 출발선은 `otel/agent.properties` 그대로(샘플러 `always_on` · 메트릭 10초 · 로그 보내기 켬). Collector `monimo-dev` 로 실제 전송
- 조건 : 맥북(도커 10코어 · 23GB), 서비스마다 **CPU 1개 · 메모리 1GB 제한**. 회차마다 `up --wait` → k6 40초 워밍업(버림) → 약 60초 측정 → `down`. MySQL 볼륨은 회차 사이에 지우지 않아 주문 표가 쌓인다
- 반복 : **85회차** · 초당 20건 70회차(`interval` 40 + `rest` 30) · 초당 40건 15회차(`check`). **반복마다 변형 순서를 한 칸 돌려** 뗌이 늘 먼저 오지 않게 했다. 표는 전부 중앙값. k6 check 실패 **0건** · 요청 수가 모자라 버린 회차 **0건**
- **`#36` 과 다른 조건 하나** : 측정 동안 **로컬 k8s 클러스터(deploy `#20` 연습판)가 같이 떠 있었다**. 쓰는 양은 1코어의 약 0.16 이고 변형끼리는 같은 조건에서 번갈아 돌렸으므로 비교는 성립하지만, **`#36` 의 절대값과 나란히 놓지 않는다**

## 한눈에

> 멘토 질문은 "줄이는 법은 무엇이고 각각 얼마를 줄이나" 였다. 답은 **"CPU 는 넷 다 못 줄인다. 메모리는 계측 범위 줄이기만 서비스마다 약 20MB 줄인다"** 다.

| 설정 | 기대했던 것 | 실제 CPU | 실제 메모리 |
|---|---|---|---|
| 메트릭 전송 간격 10초 → 30 · 60초 | 전송 횟수가 줄어 CPU | **안 줄었다** (폭이 겹친다) | 안 줄었다 |
| 트레이스 샘플링 100% → 10 · 1% | 만드는 일 · 보내는 일이 줄어 CPU | **안 줄었다** | 안 줄었다 |
| 배치 묶음 512 → 1024 · 주기 5 → 10초 | 전송 횟수가 줄어 CPU | **안 줄었다** | 안 줄었다 |
| 계측 범위 줄이기 | CPU · 메모리 둘 다 | 안 줄었다 | **줄었다 : 서비스마다 약 20MB** |

## 1. 변형끼리 안 갈린다

주문 1건당 쇼핑몰 전체 CPU(네 서비스 합 ÷ 요청 수), 초당 20건.

| 변형 | 회차 | 중앙값 | 1사분 ~ 3사분 | 회차 폭 |
|---|---|---|---|---|
| **뗌 (off)** | 15 | **11.06ms** | 10.88 ~ 11.40 | 10.40 ~ 11.64 |
| 그대로 (on) | 10 | 13.30ms | 12.48 ~ 13.36 | 12.34 ~ 19.03 |
| 전송 간격 30초 | 10 | 13.04ms | 12.74 ~ 13.41 | 12.46 ~ 15.11 |
| 샘플링 1% | 5 | 13.22ms | 12.96 ~ 13.27 | 12.86 ~ 13.30 |
| 전송 간격 60초 | 10 | 13.25ms | 12.82 ~ 13.57 | 12.40 ~ 13.99 |
| 배치 주기 10초 | 5 | 13.52ms | 13.23 ~ 13.85 | 13.13 ~ 14.16 |
| 계측 범위 줄임 | 5 | 13.56ms | 13.21 ~ 13.88 | 13.15 ~ 14.17 |
| 샘플링 10% | 5 | 13.66ms | 12.98 ~ 13.85 | 12.66 ~ 13.89 |
| 배치 묶음 1024 | 5 | 13.83ms | 13.12 ~ 13.91 | 12.91 ~ 13.98 |

- **뗌과 붙임은 깨끗하게 갈린다** : 뗌 최대 11.64 < 붙임 최소 12.34
- **붙임 변형 여덟은 하나도 안 갈린다** : 폭이 12.3 ~ 14.2 로 전부 겹친다
- 중앙값만 줄로 세우면 **설정을 줄인 쪽이 더 비싸 보인다**(배치 묶음 13.83 > 그대로 13.30). 이것은 차이가 아니라 흔들림이다. 이 표를 「순위」로 읽으면 안 된다
- 튀는 회차가 실제로 있었다 : 그대로 둔 것 10회차 중 하나가 **19.03ms** 였고 나머지 아홉은 13.37 아래였다. 중앙값으로 읽고 10회차로 둔 판단이 맞았다

### 검산 (초당 40건)

부하를 두 배로 올려 폭을 좁혀 봤다. 1차에서 중앙값이 가장 낮았던 전송 간격 30초를 **그대로 둔 것과 나란히** 놓았다.

| 변형 | 회차 | 중앙값 | 회차 폭 |
|---|---|---|---|
| 뗌 | 5 | 7.95ms | 7.64 ~ 8.14 |
| 그대로 | 5 | 9.55ms (+20%) | 9.23 ~ 9.74 |
| 전송 간격 30초 | 5 | 9.60ms (+21%) | **9.37 ~ 9.66** |

- 폭이 1차보다 훨씬 좁아졌는데도 **전송 간격 30초의 폭이 그대로 둔 것의 폭 안에 완전히 들어간다**
- 흔들림 때문에 안 갈린 것이 아니라 **차이가 없다**

## 2. 왜 안 줄었나 : 전송량은 설정대로 줄었다

수집기가 받은 건수를 회차마다 같이 기록했다(`recv_metrics` · `recv_traces`). 뗌 회차의 값이 수집기 자신의 Self-monitoring 몫이라 **배경값**이고, 쇼핑몰 몫은 그것을 뺀 값이다.

| 변형 | 받은 메트릭 건수 | 배경(618) 뺀 쇼핑몰 몫 | 받은 스팬 건수 |
|---|---|---|---|
| 뗌 | 618 | 0 | **0** |
| 그대로 (10초 · 100%) | 1,176 | **558** | 20,608 |
| 전송 간격 30초 | 804 | **186** | 20,594 |
| 전송 간격 60초 | 711 | **93** | 20,578 |
| 샘플링 10% | 1,176 | 558 | **2,058** |
| 샘플링 1% | 1,176 | 558 | **226** |
| 계측 범위 줄임 | 1,092 | 474 | 20,581 |

- 메트릭 쇼핑몰 몫이 **558 : 186 : 93 = 6 : 2 : 1** 이다. 간격 10 : 30 : 60 의 역수 그대로라 **설정이 정확히 먹었다**
- 스팬이 20,608 → 2,058 → 226 으로 **약 91배** 줄었다. 샘플러도 정확히 먹었다
- **보내는 양을 91배 줄였는데 CPU 가 그대로다** → 비용이 **보내기에 없다**
- 비용은 **계측 자체**에 있다 : 스팬을 만들고 꼬리표를 모으고 문맥을 스레드 사이로 넘기는 일
- 뗌 회차에서 스팬이 **0** 이라 `recv_traces` 는 쇼핑몰 몫만 담긴 깨끗한 열이다

## 3. 하나는 줄었다 : 계측 범위와 메모리

**`#36` 이 이미 본 것을 굳힌 것이다.** `#36` 은 원인 찾기 실험에서 「쓰는 계측만 켜면 메모리가 10 ~ 20MB 준다」 를 얻었지만 **3회차 · 번갈아 안 돌림**이라 약하다고 스스로 적어 뒀다. 이번에 5회차를 번갈아 돌려 **폭이 안 겹치는 것까지** 봤다. 발견이 아니라 확인이다.

초당 20건, 서비스별 메모리 중앙값과 회차 폭.

| 서비스 | 뗌 | 그대로 | 계측 범위 줄임 | 폭이 겹치나 |
|---|---|---|---|---|
| order | 354MB (345 ~ 358) | 442MB (433 ~ 448) | **420MB (418 ~ 428)** | **안 겹친다** |
| inventory | 334MB (316 ~ 341) | 460MB (453 ~ 469) | **440MB (434 ~ 442)** | **안 겹친다** |
| gateway | 324MB (317 ~ 334) | 405MB (389 ~ 421) | 396MB (389 ~ 400) | 겹친다 |
| payment | 324MB (315 ~ 338) | 399MB (388 ~ 409) | 393MB (382 ~ 395) | 겹친다 |

- order 와 inventory 는 **폭이 안 겹친다** : 서비스마다 약 20MB 줄었다고 말할 수 있다
- 에이전트가 더 쓰는 88 ~ 126MB 의 **약 15%** 다
- gateway 와 payment 는 폭이 겹쳐 **줄었다고 말할 수 없다**
- 나머지 변형(전송 간격 · 샘플링 · 배치)의 메모리는 그대로 둔 것과 전부 겹친다

### 스팬은 안 줄지만 잃는 것이 있다

| | 받은 스팬 건수 | 받은 메트릭 건수 (쇼핑몰 몫) |
|---|---|---|
| 그대로 | 20,608 | 558 |
| 계측 범위 줄임 | **20,581** (0.13% 차이) | **474** (84건 적다) |

- **스팬은 안 줄었다** : 끈 계측들은 스팬을 만들던 것이 아니었다. 그물에 걸려 메모리만 잡고 있었다
- **메트릭은 84건 줄었다** : 무언가가 실제로 빠졌다는 뜻이다
- `#36` 이 그 「무언가」 를 이미 짚어 뒀다 : **hikaricp 커넥션 풀 메트릭**(`db.client.connections.*`)과 **로그 MDC 의 `trace_id` 주입**(logback-mdc)이 빠진다. 내 `instr-min.yml` 도 그 둘을 안 켠다
- 메트릭 84건은 커넥션 풀 메트릭이 빠진 것과 크기가 맞는다. 다만 **어느 지표가 빠졌는지 이름으로 확인하지는 않았다**
- 켜 둔 목록 : 들어오는 요청(Tomcat · Servlet · Spring WebMVC · Spring Web) · 서비스 사이 호출(Java HTTP Client) · MySQL(JDBC) · Redis(Lettuce) · 로그 보내기(Logback) · JVM 메트릭 · 스레드를 건너는 문맥 전파(Executors)

## 4. 권고

| 설정 | 권고 | 이유 |
|---|---|---|
| 메트릭 전송 간격 | **CPU 때문에는 올리지 않는다.** 운영 30초 약속은 유지 | 올려도 CPU 가 안 준다. 다만 보내는 양이 3분의 1로 줄어 **Collector 이후**(네트워크 · Kafka · ClickHouse) 비용은 그만큼 준다. `backend PR #224` 의 약속 근거는 거기에 있다 |
| 트레이스 샘플링 | **앱 부담을 줄이는 수단으로 쓰지 않는다** | 스팬을 91배 줄여도 에이전트 CPU 가 그대로다. 운영 비율(쇼핑몰 1% · 모니모 50%, ADR `#72`)은 Collector 이후 비용을 위한 것이다 |
| 배치 묶음 · 주기 | **기본값 그대로 둔다** | 올려서 얻는 것이 없고 큐를 키우면 메모리만 늘 수 있다 |
| 계측 범위 | **메모리 권고 후보로 올린다.** 아래 셋을 확인한 뒤 넣는다 | 서비스마다 약 20MB 줄고 스팬 수는 그대로다. `#36` 의 10 ~ 20MB 를 굳힌 값이다 |

### 계측 범위를 권고로 넣기 전에 확인할 것 셋

1. **10회차로 다시 잰다** : 지금은 5회차뿐이다. order · inventory 의 폭이 안 겹치긴 했지만 간격이 5 ~ 11MB 라 회차를 더 봐야 한다
2. **빠진 메트릭 이름을 확인한다** : 메트릭 84건이 줄었다. ClickHouse 에서 지표 이름을 두 변형 사이에 대조해 무엇이 빠졌는지 적는다
3. **로그의 `trace_id` 를 확인한다** : MDC 주입이 꺼지면 로그 **문자열**에서 `trace_id` 가 빠진다. OTLP 로 보내는 로그 레코드의 `trace_id` 는 appender 가 문맥에서 직접 넣으므로 화면의 로그 · 트레이스 연결은 살아 있을 것으로 보이지만 **확인하지 않았다**

## 5. 되돌리는 조건

- **에이전트 버전을 올리면** 같은 스크립트로 다시 잰다 (`#36` 과 같은 조건)
- **쇼핑몰에 실제 업무 로직이 붙으면** 다시 잰다 : 지금 요청은 거의 일을 안 해서 에이전트 몫의 비율이 부풀려져 있다(`#36` 「읽는 법」)
- **k8s 파드 limit 이 정해지면** 그 limit 으로 다시 잰다
- **계측 범위를 운영에 넣으면** 켜 둔 목록이 곧 계약이 된다 : 새 기술(Kafka · 외부 API)을 붙일 때마다 그 목록에 추가해야 하고, 빠뜨리면 **그 구간이 트레이스에서 조용히 사라진다**. 이것이 이 설정의 가장 큰 대가다

## 6. 이 이슈에서 배운 것 (세 줄)

- **적는 일은 비용이고 보내는 일은 비용이 아니다** : `#36` 의 `metrics-off`(적는 것까지 끔)는 에이전트 CPU 의 약 5분의 1 을 가져갔는데, 이번 `interval-30 · 60`(보내는 횟수만 줄임)은 0 을 가져갔다. 두 측정을 합쳐야 비용이 어느 단계에 있는지 짚힌다
- **폭을 안 재면 중앙값 순위는 거짓말을 한다** : 중앙값만 보면 설정을 줄인 쪽이 더 비싸 보였는데 회차 폭이 전부 겹쳤다
- **예상과 반대 결과도 결과다** : 여섯 변형 중 하나도 CPU 를 안 줄였지만, 「무엇을 해도 안 된다」와 「계측 범위만 메모리를 줄인다」가 멘토 질문의 답이 됐다
