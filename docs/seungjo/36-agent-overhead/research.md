## 1. 이번 작업은 무엇을 하는 일인가

- **지금 무엇이 잘못됐나** : 비기능 요구사항에 "에이전트 오버헤드 — 대상 앱 CPU 3% 이내, 메모리 100MB 이내" 가 있는데 한 번도 재 본 적이 없다. FN-10 은 "상한 측정은 부하 테스트로 대신한다" 고만 적었고, 무엇을 무엇과 비교해 3% 인지도 정해져 있지 않다.
- **그래서 무엇을 하나** : 같은 이미지 · 같은 k6 부하로 **에이전트를 붙인 쪽과 뗀 쪽**을 돌려 CPU · 메모리 차이를 잰다. 숫자가 목표 안인지 밖인지 남기고, 밖이면 어디서 늘었는지(트레이스 · 메트릭 · 로그 · Extension)와 줄이는 손잡이를 정리한다.
- **안 하면 어떻게 되나** : "에이전트만 붙이면 된다" 는 제품 전제(ADR `#33`)에 숫자가 없다. 발표 · 면접에서 "오버헤드는요?" 에 답할 근거가 없고, 샘플링 비율(backend `#121`)을 정할 때도 비용 쪽 근거가 비어 있다.

## 2. 작업하기 전에 알아야 하는 것

### 2.1 "3%" 는 정해진 뜻이 없다

공식 문서(OTel Performance 페이지)에는 "몇 % 이내" 같은 약속이 **없다**. "앱마다 다르니 직접 재라" 가 전부다. 업계에도 하나로 정해진 정의가 없다.

| 누가 | 어떻게 말하나 |
|---|---|
| Pinpoint | "성능 · 메모리 3% 미만". TPS 와 메모리 비교. 그리고 "계측 비용은 요청당 **절대 시간**이라 가벼운 요청일수록 비율이 커 보인다" 고 경고한다 |
| Elastic APM | CPU % 없음. 지연 "한 자릿수 µs", 메모리 "몇 MB" |
| Datadog · New Relic | Java 에이전트 % 목표는 공식 문서에서 확인 못 함 |

우리 요구사항의 3% 는 Pinpoint 숫자를 가져온 것으로 보인다. 그래서 먼저 정해야 하는 것은 **무엇을 나눠서 3% 인가** 다. 후보는 둘이다.

```
상대 증가율 : (붙인 쪽 CPU 초 − 뗀 쪽 CPU 초) / 뗀 쪽 CPU 초        ← 같은 요청 수 기준
절대 %p    : 붙인 쪽 CPU% − 뗀 쪽 CPU%  (예 : 12% → 15% 면 3%p)
```

절대 %p 는 부하를 얼마나 거느냐에 따라 의미가 바뀐다(초당 1건이면 무조건 통과, 포화면 무조건 실패). 상대 증가율은 부하 크기와 덜 엮인다. 다만 Pinpoint 경고처럼 우리 쇼핑몰은 요청 하나가 아주 가벼워서(DB 한두 번, HTTP 한두 번) **상대 증가율이 크게 나올 가능성이 높다**. 이 점은 5 절 실험에서 바로 볼 것이다.

### 2.2 메모리 100MB 는 "어느 숫자" 인가

JVM 메모리는 층이 여러 개라 무엇을 재느냐로 숫자가 크게 달라진다.

```
컨테이너가 쓰는 메모리 (docker stats MEM = cgroup usage − inactive_file)
 ├─ 힙            : 객체. GC 가 -Xmx 안에서 늘였다 줄였다 한다  ← 에이전트의 스팬 · 큐 객체도 여기
 ├─ 비힙          : metaspace(클래스 정보) · code cache(JIT 결과)  ← 에이전트 클래스 수천 개가 여기
 ├─ 스레드 스택    : 스레드마다 약 1MB 예약                         ← 에이전트 스레드 약 12개 + Extension 1개
 └─ 기타 네이티브  : direct buffer(gRPC/Netty) · GC 자료구조 등
```

| 재는 법 | 장점 | 단점 |
|---|---|---|
| `docker stats` MEM / cgroup `memory.current` | 컨테이너 바깥에서 재서 붙임 · 뗌 똑같이 잴 수 있다. "대상 앱이 실제로 먹는 양" 에 가장 가깝다 | 힙이 GC 따라 출렁여서 값이 흔들린다 |
| `jvm.memory.used` (OTel 메트릭) | 힙 · 비힙을 풀별로 나눠 준다. 이미 ClickHouse 에 들어오고 있다 | **에이전트가 내는 값이라 뗀 쪽에서는 없다.** 비교 불가 |
| NMT (`-XX:NativeMemoryTracking=summary` + `jcmd VM.native_memory`) | 힙 · 클래스 · 스레드 · 코드 · GC 를 항목별로 쪼개 준다. 원인 찾기에 좋다 | 켜면 그 자체로 5~10% 느려진다. **CPU 를 재는 회차에는 끈다** |

웹 리서치 권고는 "주 지표는 컨테이너 메모리 차이, 원인은 NMT 로" 다. 힙 출렁임을 없애려면 `-Xms` = `-Xmx` 로 힙 크기를 고정하는 방법이 있다. 그러면 차이가 비힙 · 스레드 쪽으로 모인다.

**우리 쪽에서 반드시 알아야 할 것** : 지금 compose 의 쇼핑몰 컨테이너에는 **CPU · 메모리 제한이 없다**. 도커에 잡힌 자원은 10코어 · 16GB 다. JVM 은 컨테이너 메모리의 25% 를 최대 힙으로 잡으므로 최대 힙이 약 4GB 가 된다. 힙이 넉넉하면 GC 가 게을러져 메모리가 쭉 늘어난 채로 있고, 붙임 · 뗌 차이가 GC 타이밍에 묻힌다. 측정할 때는 k8s 에서 쓸 것과 비슷한 제한(`--cpus` · `mem_limit`)을 걸어야 숫자가 의미 있다.

### 2.3 에이전트를 떼는 공정한 방법

| 방법 | 무엇이 남나 |
|---|---|
| A. `OTEL_JAVAAGENT_ENABLED=false` | 공식 문서는 "에이전트를 통째로 끈다" 고 한다. 소스를 보면 에이전트 jar 를 읽고 클래스로더를 하나 만든 뒤, 계측 설치 · SDK · Extension · `AgentListener` 를 **전부 건너뛴다**. 남는 비용은 jar 로딩 정도로 작다(수치 미확인) |
| B. `-javaagent` 줄을 아예 뺀다 (entrypoint 덮어쓰기) | 진짜 0. OTel 공식 벤치마크의 "none" 이 이쪽이다 |

같은 이미지로 env 하나만 바꾸면 되는 A 가 편하고, "깨끗한 비교" 는 B 다. compose 에서는 둘 다 덮어쓰기 파일 하나로 된다.

### 2.4 우리 설정에서 무엇이 비용을 키우나

| 설정 | 우리 값 | OTel 기본값 | 비용에 미치는 것 |
|---|---|---|---|
| 샘플러 | `always_on` (전부) | `parentbased_always_on` (사실상 전부) | 요청마다 스팬 생성 · 큐 · 직렬화 · 전송. 가장 큰 몫 |
| 메트릭 간격 | **10초** | 60초 | 6배 자주 모아서 보낸다 |
| 로그 보내기 | `otlp` (켬) | `otlp` | 앱 로그 한 줄마다 레코드 하나 |
| 스팬 큐 | 기본 | 2048개 · 512개씩 · 5초마다 | 큐가 가득 차면 그만큼 힙을 잡는다 |
| 계측 개수 | 기본(전부 켬) | 전부 켬 | 클래스 변환 → 시작 시간 · metaspace |
| Extension (`#34`) | 데몬 스레드 1개, 25초마다 GET 1번 | — | 평소엔 거의 0 이어야 한다. 덤프 순간만 safepoint |

쇼핑몰은 한 요청이 Redis · MySQL · HTTP 호출을 줄줄이 만들어 **요청당 스팬이 많다**(주문 1건 = 게이트웨이 · 주문 · 재고 · 결제 · DB 여러 줄). OTel Performance 페이지가 "JDBC · Redis 처럼 스팬을 많이 만드는 계측" 을 비용 요인으로 꼽은 그대로다.

### 2.5 CPU 를 흔들리지 않게 재는 법

- **부하는 고정 요청률**로 건다. k6 `constant-arrival-rate` 는 응답이 느려져도 초당 요청 수를 유지한다(우리 `k6/order.js` 가 이미 이 방식). 붙인 쪽이 느려서 요청을 덜 받으면 CPU 가 오히려 적게 나오는 착시를 막는다
- **순간값(`docker stats` CPU%)보다 누적값 차이**를 쓴다. 측정 구간 시작 · 끝에 cgroup `cpu.stat` 의 `usage_usec` 를 읽어 빼면 "이 구간에 쓴 CPU 초" 가 나온다. 요청 수로 나누면 **요청당 CPU** 다
- **JIT 워밍업을 버린다.** 막 뜬 JVM 은 해석 실행이라 느리다. 공식 벤치는 30초 버린다
- **번갈아 여러 번** 돌리고 중앙값을 본다(붙임 → 뗌 → 붙임 …). 맥북에서 다른 프로그램 · 열 때문에 생기는 흔들림을 섞어서 지운다
- 부하는 **포화되지 않는 선**에서 건다. 머신 CPU 가 꽉 차면 둘 다 100% 근처라 차이가 안 보인다(공식 벤치가 이 상태라 CPU 차이를 읽기 어렵다)

### 2.6 남은 얼마가 나왔나

| 출처 | 시작 시간 | 메모리 | CPU · 지연 |
|---|---|---|---|
| OTel 공식 야간 벤치 (2026-10-07, petclinic, 5명 · 5000회) | 8.8 → 12.4초 (+3.6초) | 최소 힙 123 → 222MB, 스레드 39 → 51, 할당량 +26% | 머신이 97% 포화라 CPU 비교 불가. p95 8.69 → 9.21ms |
| Elastic EDOT Java (OTel 기반, 날짜 · 버전 미기재) | 5.55 → 6.82초 | — | 시스템 CPU 53.82 → 54.25% (+0.43%p), p95 1.96 → 2.06ms |
| OTel PR #20003 (2 CPU · 1GiB) | 1.66 → 4.48초 | — | — |

읽을 것 : 메모리는 **최소 힙만 약 100MB 늘었다**. 비힙 · 스레드까지 더하면 100MB 목표는 빠듯할 수 있다. 시작 시간은 수 초 늘어나는 게 정상이고 우리 목표에는 시작 시간이 없다.

### 2.7 지금 이미 있는 숫자

에이전트가 이미 ClickHouse `monimo.metrics_raw` 에 JVM 지표를 보내고 있다 : `jvm.cpu.recent_utilization` · `jvm.cpu.time` · `jvm.memory.used` · `jvm.memory.committed` · `jvm.thread.count` · `jvm.gc.duration` 등. **붙인 쪽의 내부 분해**(힙 · 비힙 · 스레드 수)에는 쓸 수 있지만 뗀 쪽에는 없으므로 **붙임 · 뗌 비교의 기준은 컨테이너 바깥(cgroup)** 이어야 한다.

`jvm.cpu.recent_utilization` 은 "머신 전체 코어 대비" 비율이라 10코어 머신에서 한 코어를 꽉 써도 0.1 이다. 3% 를 이 값으로 읽으면 안 된다.

### 2.8 측정 흐름

```
(한 회차)
compose up (붙임 또는 뗌, CPU · 메모리 제한 같게)
  → healthy 대기
  → k6 워밍업 (고정 RPS, 버림)
  → cgroup cpu.stat · memory 읽기 (시작)
  → k6 본 측정 (고정 RPS, N초)
  → cgroup 읽기 (끝) + k6 결과(처리량 · p95 · 실패율)
  → compose down
번갈아 반복 → 서비스별 중앙값 표
```

| 질문 | 답 |
|---|---|
| 무엇을 비교하나 | 같은 이미지에서 에이전트 붙임 vs 뗌. 같은 제한, 같은 부하 |
| 어디서 재나 | 컨테이너 cgroup (CPU 초 · 메모리). 지연 · 처리량은 k6 |
| 무엇을 만드나 | 측정 스크립트 + 결과 표. 앱 · 에이전트 설정은 안 바꾼다 |
| 누구 거를 건드리나 | 내가 띄운 쇼핑몰 컨테이너만. monimo-dev Collector · Kafka · CH 는 그대로 두고 데이터만 받는다 |

### 2.9 자주 헷갈리는 것

| 헷갈리는 것 | 실제 |
|---|---|
| "CPU 3%" 는 정해진 업계 기준이다 | 아니다. 무엇 대비인지 우리가 정해야 한다(상대 증가율 vs 절대 %p) |
| `docker stats` 의 CPU% 를 보면 된다 | 순간값이라 흔들린다. 구간 누적(`cpu.stat usage_usec`) 차이가 낫다 |
| 에이전트 메트릭(`jvm.*`)으로 비교하면 된다 | 뗀 쪽엔 그 메트릭이 없다. 비교는 바깥에서 |
| 메모리 차이 = 힙 차이 | 힙은 GC 따라 출렁인다. 에이전트 몫은 비힙(클래스) · 스레드에 많다 |
| `OTEL_JAVAAGENT_ENABLED=false` 면 jar 가 아예 안 올라간다 | jar 는 올라가고 설치만 건너뛴다. 진짜 0 은 `-javaagent` 를 빼는 것 |
| 컨테이너에 제한이 없으니 공정하다 | 오히려 반대. 최대 힙 약 4GB 라 GC 타이밍에 차이가 묻힌다 |
| Extension 은 오버헤드가 없다 | 평소엔 거의 0 이어야 하지만 재 본 적은 없다. 이번에 같이 잰다 |
| 시작이 느려지면 목표 위반이다 | 목표는 CPU · 메모리뿐이다. 시작 시간은 참고로만 적는다 |

## 3. 1차 질문 (사람 차례)

**Q1. Pinpoint 공식 문서에 "성능 · 메모리 3% 미만" 이 나오나?**

나온다. 두 곳이다.
- Pinpoint 성능 문서(pinpoint-apm.github.io `performance.md`) : "Test result shows that Pinpoint affects less than 3% in performance and memory". 그리고 "트랜잭션이 DB 를 거치지 않으면 3% 보다 훨씬 많이 쓰는 것처럼 보일 수 있다. 계측 시간은 상대가 아니라 절대이기 때문" 이라고 단서를 단다
- Pinpoint 레포 README : "approximately 3% increase in resource usage"
- 시험 조건 : Tomcat, JVM 1.8, G1, **힙 `-Xms4g -Xmx4g` 고정**, Cubrid DB, nGrinder 부하. 안 붙임 vs 5% 샘플링 vs 100% 추적을 비교했다

우리 요구사항의 3% 는 이 숫자를 가져온 것이고, Pinpoint 도 힙을 고정해 놓고 쟀다는 점이 2.2 의 "힙 고정" 과 맞는다.

**Q2. 상대 증가율과 절대 %p, 골랐을 때 장단점은?**

예 : 뗀 쪽 CPU 10%, 붙인 쪽 12%.

| | 상대 증가율 | 절대 %p |
|---|---|---|
| 계산 | (12 − 10) / 10 = **20%** | 12 − 10 = **2%p** |
| 장점 | 부하를 바꿔도 값이 비교적 일정하다(요청당 비용 비율). Pinpoint · OTel 벤치가 쓰는 뜻에 가깝다 | 직관적이다("CPU 2% 더 쓴다"). 운영자가 노드 여유를 볼 때 바로 쓴다 |
| 단점 | 요청이 가벼운 앱은 크게 나온다. 우리 쇼핑몰은 거의 일을 안 하므로 3% 를 넘기 쉽다 | 부하를 낮추면 무조건 통과, 높이면 무조건 실패. "초당 몇 건에서" 를 같이 안 적으면 숫자가 의미 없다 |
| 우리에게 | 정직하지만 목표 실패가 나올 가능성 큼 | 통과는 쉽지만 부하를 같이 적어야 한다 |

둘 다 재서 같이 적는 것도 가능하다(같은 측정에서 둘 다 나온다). 고르는 건 5 절.

**Q3. 힙 · 비힙 · 스레드 스택 · 기타 네이티브는 각각 무엇인가?**

- **힙** : `new` 로 만든 객체가 사는 곳. GC 가 청소한다. 에이전트 몫 = 스팬 · 로그 레코드 객체, 내보내기 전 큐(최대 2048개). `-Xmx` 가 상한
- **비힙** : 객체가 아니라 "코드에 대한 정보". metaspace = 로드한 클래스 정의(에이전트는 계측 클래스 수천 개를 싣는다), code cache = JIT 가 기계어로 바꾼 코드. 에이전트 몫이 큰 곳
- **스레드 스택** : 스레드마다 호출 기록을 쌓는 칸(기본 최대 1MB 예약, 실제 쓰는 만큼만 잡힘). 에이전트는 내보내기 · gRPC 스레드 약 12개, Extension 1개를 더한다
- **기타 네이티브** : JVM 바깥 C 메모리. gRPC(Netty) 가 쓰는 direct buffer, GC 자체 장부 등

컨테이너 메모리 = 이 넷의 합에 가깝다. 힙만 보면 에이전트 몫을 놓친다.

**Q4. 재는 법 셋의 설명과 장단점**

| 재는 법 | 무엇인가 | 장점 | 단점 |
|---|---|---|---|
| `docker stats` MEM / cgroup `memory.current` | 운영체제가 "이 컨테이너가 지금 쓰는 메모리" 로 세는 값 | 붙임 · 뗌 똑같이 잴 수 있다. k8s 메모리 limit 과 같은 기준이라 실제로 OOM 이 나는 숫자 | 힙이 GC 따라 출렁여 흔들린다 → 힙 고정 · 여러 번 · 정상 상태 값 |
| `jvm.memory.used` | 에이전트가 JVM 에게 물어 보내는 풀별 사용량 | 힙 · metaspace · code cache 가 따로 보인다. 이미 CH 에 있다 | 에이전트가 만드는 값이라 **뗀 쪽엔 없다**. 스레드 스택 · direct buffer 일부는 빠진다 |
| NMT + `jcmd` | JVM 이 스스로 "어디에 몇 MB" 를 항목별로 장부에 적게 하는 옵션 | 클래스 · 스레드 · 코드 · GC · 내부까지 쪼갠다. 붙임 · 뗌 둘 다 켤 수 있다 | 켜면 5~10% 느려진다. 그래서 CPU 재는 회차와 분리 |

**Q5. 에이전트는 왜 빼나?**

오버헤드 = "붙였을 때 − 안 붙였을 때" 다. 뺄셈의 기준(안 붙인 쪽)이 있어야 차이가 나온다. 붙인 쪽 하나만 재면 "CPU 12%" 는 나오지만 그중 에이전트 몫이 얼마인지 모른다. 그래서 같은 이미지에서 에이전트만 빼고 한 번 더 잰다. 운영에서 빼자는 뜻이 아니다.

**Q6. 2.4 설정들은 각각 무엇인가?**

- **샘플러 `always_on`** : 요청 몇 개를 트레이스로 남길지. `always_on` 은 100%. 10% 로 낮추면 스팬 만드는 일 · 보내는 일이 대략 그만큼 준다. 단 백엔드 `#121` 샘플링은 Collector 에서 거르는 것이라 **에이전트 비용은 안 줄인다**
- **메트릭 간격 10초** : JVM · HTTP 메트릭을 모아 보내는 주기. 기본 60초인데 우리는 화면 반응을 위해 10초. 6배 자주 모으고 보낸다
- **로그 보내기 `otlp`** : 앱이 찍는 로그 한 줄을 에이전트가 가로채 Collector 로도 보낸다. 로그가 많을수록 비용
- **스팬 큐 2048 · 512 · 5초** : 스팬을 바로 보내지 않고 큐에 모았다가 5초마다(또는 512개 차면) 한 배치씩 보낸다. 큐 최대 2048개가 힙을 잡는다. 넘치면 버린다
- **계측 개수** : 에이전트에는 Spring · JDBC · Redis · HTTP 등 계측 수백 개가 들어 있고 기본으로 다 켜져 있다. 켜진 만큼 시작할 때 클래스를 고쳐 쓰는 일과 metaspace 가 는다
- **Extension** : `#34` 데몬 스레드. 25초마다 GET 한 번, 나머지는 대기라 거의 0 이어야 한다

**Q7. 2.5 측정 요령 다섯 줄 쉽게**

- **고정 요청률** : "초당 50건" 을 응답이 늦든 빠르든 계속 넣는다. 사람 수 고정 방식이면 느린 쪽(붙인 쪽)이 요청을 덜 받아 CPU 가 적게 나오는 착시가 생긴다
- **누적값 차이** : 순간 CPU% 는 0.5초마다 오르내린다. 대신 "지금까지 쓴 CPU 시간 총합" 계기판을 시작 · 끝에 읽어 빼면 그 구간에 쓴 CPU 가 정확히 나온다. 자동차 순간 연비 대신 주행 전후 주유량을 보는 것과 같다
- **워밍업 버리기** : 막 뜬 JVM 은 코드를 한 줄씩 해석하다가 자주 쓰는 곳을 기계어로 바꾼다(JIT). 처음 30초는 느리고 CPU 를 많이 써서 버린다
- **번갈아 반복 · 중앙값** : 맥북은 다른 앱 · 발열 때문에 회차마다 흔들린다. 붙임 → 뗌 → 붙임 … 순서로 번갈아 여러 번 돌리고 가운데 값을 본다. 한쪽만 운 나쁜 회차에 몰리지 않게
- **포화 피하기** : CPU 가 100% 면 둘 다 100% 라 차이가 안 보인다. 여유 있는 부하에서 잰다

**Q8. 2.6 출처들은 무엇인가?**

- **OTel 공식 야간 벤치** : OTel Java 에이전트 레포에 있는 `benchmark-overhead` 모듈. 매일 밤 GitHub 에서 Spring 예제 앱(petclinic)에 k6 부하를 걸어 "에이전트 없음 vs 최신 릴리스" 를 자동 비교하고 결과 파일을 커밋한다. 공식이지만 머신 CPU 가 97% 로 포화라 CPU 비교에는 못 쓴다
- **Elastic EDOT Java** : Elastic 이 OTel 에이전트를 자기 설정으로 감싸 배포하는 판. 자체 측정 결과를 문서에 올렸다. 버전 · 날짜가 안 적혀 있어 참고만
- **OTel PR #20003** : 시작 시간을 줄이는 작업(AOT 캐시) PR 에 첨부된 측정. 2 CPU · 1GiB 컨테이너라 우리 k8s 조건과 비슷하다. 시작 시간만 있다

**Q9. cgroup 이 무엇인가?**

리눅스 커널이 **프로세스 그룹에 자원 장부와 한도를 붙이는 기능**이다(control group). 도커 컨테이너 하나 = cgroup 하나다. 커널이 그 그룹이 지금까지 쓴 CPU 시간, 지금 쓰는 메모리를 파일로 보여 준다.

```
컨테이너 안 /sys/fs/cgroup/
  cpu.stat        usage_usec 123456789   ← 지금까지 쓴 CPU 시간(마이크로초) 누적
  memory.current  412000000             ← 지금 쓰는 메모리(바이트)
  memory.peak     450000000             ← 최고점
  cpu.max · memory.max                   ← --cpus · mem_limit 로 건 한도
```

`docker stats` · k8s `kubectl top` · OOM Kill 이 전부 이 장부를 본다. JVM 바깥에서 재기 때문에 에이전트가 있든 없든 똑같이 읽을 수 있어서 비교 기준으로 쓴다. 맥 도커 데스크톱은 리눅스 VM 안에서 돌므로 똑같이 있다.

**Q10. 내가 이해한 것 맞나? (승조 정리 → 고칠 곳)**

| 승조 정리 | 맞나 | 고칠 곳 |
|---|---|---|
| 힙 : 스팬이 만들어져 큐에 있다가 전송되면 힙이 비워진다 | 거의 맞다 | 전송 즉시 비워지는 게 아니라 **쓰레기가 되고, GC 가 돌 때 비워진다**. 그래서 에이전트는 메모리보다 "GC 일거리(할당량 +26%)" 로 CPU 를 더 쓴다 |
| 비힙 : 앱 중간중간 추적 코드를 넣어야 하고 그 코드가 비힙에 들어가서, 추적할 대상이 많을수록 비힙이 찬다 | 맞다 | 정확히는 두 덩어리다. ① 에이전트 자기 클래스(SDK · 내보내기 · Byte Buddy) : 대상과 상관없이 고정 ② 계측에 걸린 앱 클래스를 고쳐 쓴 결과 + 그 계측의 도우미 클래스 : 걸린 대상이 많을수록 증가. JIT 기계어(code cache)도 같이 는다 |
| 스레드 스택 : Extension 스레드가 많아지면 는다 | 반만 맞다 | Extension 은 스레드 1개뿐이다. 대부분은 **에이전트 자체 배경 스레드**(스팬 · 로그 내보내기, 메트릭 수집, gRPC 연결) 약 12개다. 스레드당 최대 1MB 예약이지만 실제로 쓰는 만큼만 잡힌다 |
| 기타 네이티브 : JVM 바깥 메모리 | 맞다 | 에이전트 몫은 gRPC(Netty) 버퍼가 대표 |
| 주 지표는 `docker stats` MEM / cgroup `memory.current`, 원인 분석은 NMT | 확정 | — |
| `OTEL_JAVAAGENT_ENABLED=false` 는 부팅 때 jar 를 읽어 미세하게 남으니, 엄밀하게는 `-javaagent` 를 완전히 뺀다 | 맞다 | compose 덮어쓰기 파일에서 `entrypoint` 를 바꾸면 된다. Extension 도 같이 빠진다 |
| 계측 개수 : 에이전트 안 그물망이 서비스 기술스택에 매칭되니, 스택이 많을수록 비힙을 먹는다. 쓰는 것만 켜는 게 좋다 | 거의 맞다 | 걸리지 않는 그물(안 쓰는 기술)은 **비힙을 거의 안 먹는다**. 대신 시작할 때 모든 클래스를 그물 수백 개에 대 보는 비용(시작 시간 · CPU)이 든다. 그래서 "안 쓰는 것 끄기" = 시작 시간 절약, "쓰지만 필요 없는 것 끄기"(예 : 로그 보내기) = 메모리 · CPU 절약 |
| OTel 야간 벤치 : 메모리 오버헤드는 사실상 불가능하다 | 틀림 | "메모리가 늘어난다(최소 힙 약 +100MB)" 는 숫자다. 읽기 어려운 건 **CPU** 다(머신 97% 포화). 우리 100MB 목표가 빠듯할 수 있다는 근거 |
| Elastic EDOT : CPU 도 어쩔 수 없이 늘어난다 | 반만 맞다 | 늘긴 하지만 **작다**(+0.43%p, 절대 기준) 는 숫자다 |
| PR #20003 : 부팅시간 줄이는 거 | 맞다 | 그 PR 에 첨부된 측정이 "에이전트가 작은 컨테이너에서 시작을 약 2.8초 늦춘다" 를 보여 준다. 시작 시간은 우리 목표에 없어 참고만 |
| 비교는 cgroup, `jvm.memory.used` 는 떼면 사라지니 안 쓴다 | 맞다 | 비교에는 안 쓰고, **붙인 쪽 안을 쪼개 보는 보조**로는 쓸 수 있다(이미 CH 에 있다) |
| `jvm.cpu.recent_utilization` 은 컨테이너가 아니라 서버 기준이라 안 쓴다 | 결론은 맞다 | 안 쓰는 진짜 이유는 **떼면 사라진다** 는 것. "서버 전체 코어 대비" 는 지금 compose 에 CPU 제한이 없어 10코어 = 머신 전체라서 그런 것이고, 제한을 걸었을 때 컨테이너 기준으로 바뀌는지는 확인 못 했다(5 절 실험에서 볼 것) |
| healthy 대기는 건강한 상태에서 테스트하려고 | 맞다 | 더 정확히는 **부팅 비용을 측정에서 빼려는 것**. 부팅(스프링 · DB 연결 · 에이전트 설치)은 CPU 를 크게 쓴다. healthy = 부팅 끝, 그 뒤 워밍업 = JIT 데우기. 둘은 다른 단계다 |

## 4. 1차 정리

**정해진 것 (3 절 대화에서)**

- 오버헤드 = 같은 이미지 · 같은 부하에서 "붙였을 때 − 뗐을 때". 뗀 쪽은 **`-javaagent` 를 완전히 뺀다**(compose 덮어쓰기로 `entrypoint` 교체). `OTEL_JAVAAGENT_ENABLED=false` 는 jar 를 읽어 미세하게 남으므로 쓰지 않는다
- 메모리 주 지표는 **컨테이너 cgroup `memory.current`**(= `docker stats` MEM 계열). 원인 분석은 **NMT**, NMT 는 CPU 회차와 분리
- CPU 는 **cgroup `cpu.stat usage_usec` 구간 차이**(누적). `docker stats` 순간 CPU% 는 안 쓴다
- `jvm.*` 메트릭은 뗀 쪽에 없으므로 **비교에는 안 쓰고** 붙인 쪽 내부를 볼 때 보조로만 쓴다
- 부하는 **고정 요청률**(`constant-arrival-rate`), healthy(부팅 끝) → 워밍업(JIT) 버림 → 본 측정 순서. 포화되지 않는 선에서, 번갈아 여러 번

**머리에 남길 그림**

```
에이전트 비용이 가는 곳
  힙     : 스팬 · 로그 객체 → 보내면 쓰레기 → GC 가 치움   ⇒ 메모리보다 GC CPU
  비힙   : 에이전트 자기 클래스(고정) + 그물에 걸린 앱 클래스 고쳐 쓰기(스택 따라)
  스레드 : 에이전트 배경 스레드 약 12 + Extension 1
  네이티브 : gRPC 버퍼
```

**아직 안 정한 것 (5 절)**

① CPU 3% 를 무엇으로 읽나(상대 · 절대 · 둘 다) ② 컨테이너 제한(CPU · 메모리)을 얼마로 거나 ③ 힙을 고정하나 ④ 부하 크기 · 길이 · 반복 횟수 ⑤ 서비스별로 보나 합으로 보나 ⑥ 스크립트와 결과를 어디에 남기나 ⑦ 목표를 넘으면 이번에 손잡이까지 돌려 보나

## 5. 선택지와 설명

### 5.0 먼저 돌려 본 것 (파일럿, 2026-10-08 ~ 09)

조건 : 맥북(도커 10코어 · 16GB), 쇼핑몰 네 서비스 각각 **CPU 1개 · 메모리 1GB 제한**, 그 외 compose 그대로(Collector monimo-dev 로 실제 전송). 한 회차 = `up --wait` → k6 40초 워밍업(버림) → cgroup 읽기 → k6 60초 → cgroup 읽기 → `down`. 뗀 쪽은 `entrypoint` 를 `java -jar /app/app.jar` 로 덮어써 `-javaagent` 를 뺐다. 스크립트는 스크래치(아직 레포에 없음).

**① 초당 20건, 붙임 3회 · 뗌 3회 번갈아, 중앙값** (CPU 는 60초 동안 쓴 CPU 초, 1코어 기준 %)

- 그래서 **절대 %p 는 부하를 2배로 하면 대략 2배**가 된다. 초당 20건이면 3%p 안, 40건이면 세 서비스가 3%p 밖

**③ 손잡이를 돌려 보면** (초당 20건, 각 1회, 상대 증가)

| | gateway | order | payment | inventory |
|---|---|---|---|---|
| 그대로 (중앙값) | +18% | +14% | +13% | +24% |
| 샘플링 10% (`parentbased_traceidratio` 0.1) | +16% | +14% | +10% | +20% |

- 남는 후보(확인 안 함) : 요청마다 계측 코드가 도는 일 자체(컨텍스트 전파, 헤더 주입, 스팬 객체 생성) + **HTTP · DB 지연 히스토그램 메트릭은 샘플링과 상관없이 모든 요청에 기록**된다. 이 둘을 가르려면 메트릭 끄기(`OTEL_METRICS_EXPORTER=none`) · 계측 일부 끄기 실험이 더 필요하다

**④ 메모리를 NMT 로 쪼개 보면** (초당 20건 끝난 뒤, 붙임 − 뗌, JVM 이 잡은 committed)

| 항목 | gateway | order | payment | inventory | 뜻 |
|---|---|---|---|---|---|
| 클래스 수 | +5,108 | +5,227 | +5,016 | +5,676 | 에이전트 · 계측 클래스 |
| Metaspace + Class | +25MB | +26MB | +25MB | +28MB | 클래스 정의 |
| Code (JIT) | +8MB | +11MB | +8MB | +11MB | 에이전트 코드도 기계어로 |
| Symbol · Compiler · 기타 | +22MB | +8MB | +12MB | +18MB | 클래스 이름표, JIT 작업 공간(출렁임) |
| 스레드 수 (스택) | +11 (+1MB) | +12 (+1MB) | +12 (+2MB) | +13 (+2MB) | 스택은 작다 |
| 힙 | +47MB | +53MB | +10MB | +53MB | **회차마다 크게 출렁** |
| 합 (NMT) | +103MB | +99MB | +57MB | +112MB | |

- 힙 아닌 쪽(클래스 · 코드 · 이름표 등)이 **서비스마다 약 45 ~ 60MB**. 에이전트를 붙이는 한 고정으로 드는 몫이다
- 힙 몫은 0 ~ 50MB 로 출렁인다. GC 가 언제 돌았느냐에 달렸다
- cgroup 은 `anon`(프로세스가 쓴 메모리)이 거의 전부이고 `file`(파일 캐시)은 0 이었다. 에이전트 jar 를 읽은 캐시가 섞이는 문제는 없다

**⑤ 힙을 256MB 로 고정해 보면** (`-Xms256m -Xmx256m`, 2회) : 메모리 차이 +21 ~ +121MB 로 **오히려 더 흔들렸다**. `-Xms` 는 힙을 "예약" 만 하고 실제로 건드린 페이지만 cgroup 에 잡히기 때문이다. 고정의 효과가 없다

**⑥ 흔들림** : 뗌 회차 하나(`hf-off2`)가 p95 25ms · CPU +20% 로 튀었다. 맥북에서 한두 회차는 이렇게 튄다. 판정에는 **5회 이상 번갈아 중앙값**이 필요하다

**⑦ 2.7 정정** : `jvm.cpu.recent_utilization` 이 "머신 전체 코어 대비" 라고 썼는데, CPU 1개 제한을 걸자 `jvm.cpu.count` 가 1 이 됐다. **제한을 걸면 컨테이너 기준**이다. 그래도 뗀 쪽에 없으니 비교에는 안 쓴다는 결론은 같다

### 5.1 파일럿이 말해 주는 것 (세 줄)

- **CPU** : 상대 증가율로는 13 ~ 24% 로 3% 를 크게 넘는다. 절대 %p 로는 초당 20건에서 0.8 ~ 1.6%p 로 안이지만 40건이면 넘는다. 즉 "3%" 의 뜻을 정하지 않으면 통과도 실패도 말할 수 없다
- **메모리** : 약 90 ~ 140MB, 가만히 있어도 약 110MB. 100MB 는 **경계이거나 조금 넘는다**. 고정 몫(클래스 · 코드 등) 약 45 ~ 60MB 는 에이전트를 붙이는 한 남는다(계측을 끄면 일부 준다)
- **샘플링 · 로그 · 메트릭 간격으로는 안 줄어든다.** 줄이려면 계측 자체를 덜 도는 쪽(안 쓰는 계측 끄기)을 봐야 한다

### 5.2 정할 것과 선택지

**A. "CPU 3%" 를 무엇으로 읽나**

| | 방법 | 우리 결과 | 장점 | 단점 |
|---|---|---|---|---|
| A1 | 상대 증가율 (같은 부하에서 CPU 초 비율) | 13 ~ 24% **실패** | 부하 크기와 덜 엮인다. Pinpoint 문구에 가장 가깝다 | 쇼핑몰은 요청이 거의 일을 안 해서 크게 부풀려진다(Pinpoint 도 경고). 실제 서비스면 더 작게 나온다 |
| A2 | 절대 %p (정한 부하에서, 1코어 기준) | 20건 : 0.8 ~ 1.6%p **통과** / 40건 : 2.8 ~ 4.5%p **실패** | 운영자에게 직관적 | 부하를 고르는 순간 결과가 정해진다. 부하를 같이 안 적으면 의미 없다 |
| A3 | 요청당 추가 CPU (ms) | 주문 1건당 +1.7ms (네 서비스 합) | 부하 · 앱 크기와 무관한 "에이전트 단가". 비교 · 회귀 감시에 좋다 | 3% 라는 요구사항 문장과 바로 대응이 안 된다 |
| **A4 (추천)** | **셋 다 재서 적고, 판정은 A1 로 하되 "가벼운 앱이라 부풀려진다" 를 같이 적는다** | 실패 + 이유 | 숫자를 숨기지 않는다. 요구사항을 고칠지 팀이 판단할 재료가 된다 | 요구사항 "3% 이내" 를 못 지켰다고 써야 한다 |

A2 로 "통과" 를 쓰는 건 부하를 골라서 통과시키는 것이라 추천하지 않는다.

**B. 메모리 기준**

| | 방법 | 우리 결과 | 장단점 |
|---|---|---|---|
| **B1 (추천)** | cgroup `memory.current` 차이, 부하 중 · 5회 중앙값 | 약 90 ~ 140MB | 운영에서 OOM 이 나는 숫자. 출렁임은 반복으로 누른다 |
| B2 | 가만히 있을 때(부하 0) 차이 | 약 110MB | 가장 안정적. 하지만 부하 중 힙 몫이 빠진다 |
| B3 | NMT 합 차이 | 57 ~ 112MB | 쪼개 보기엔 최고. JVM 밖 메모리 일부가 빠지고 NMT 자체가 비용 |

B1 로 판정, B2 · NMT 는 같이 적는다(4 절에서 정한 대로).

**C. 컨테이너 제한**

| | 값 | 장단점 |
|---|---|---|
| **C1 (추천)** | 서비스마다 CPU 1개 · 메모리 1GB | 파일럿 조건 그대로. k8s 에 올릴 때 첫 limit 후보로도 쓸 수 있다 |
| C2 | CPU 0.5 · 512MB | k8s 에서 흔한 작은 파드. 최대 힙이 128MB 로 작아져 GC 가 바빠지고 에이전트 몫이 더 커 보일 수 있다 |
| C3 | 제한 없음 | 지금 compose 그대로. 2.2 에서 본 대로 비교가 흐려진다 |

**D. 힙 고정** : 파일럿 ⑤ 에서 효과가 없었다. **고정하지 않는다**(추천). `-XX:+AlwaysPreTouch` 로 힙을 미리 다 건드리면 고정되지만, 그러면 힙 몫(에이전트가 만드는 객체)이 아예 안 보이게 된다.
