## 읽는 법

- **상대 증가율이 큰 이유** : 쇼핑몰 요청은 거의 일을 안 한다(DB 한두 번, HTTP 한두 번, 요청당 앱 CPU 수 ms). 에이전트 비용은 요청당 **절대 시간**(주문 1건에 약 3 ~ 4ms, HTTP 요청 1.5건분)이라 가벼운 앱일수록 비율이 부풀려진다. Pinpoint 문서도 같은 경고를 한다. 실제 업무 로직이 있는 서비스라면 같은 3 ~ 4ms 가 훨씬 작은 비율이 된다. 다만 "우리 쇼핑몰에서는 20% 대" 가 실측이다
- **절대 %p 는 부하에 비례한다** : 10 → 20 → 40건에서 대략 1 → 2 → 3%p. 초당 40건(파드 하나, CPU 1개)에서 order · inventory 가 3%p 를 넘는다. 부하를 골라 "통과" 라고 쓰지 않으려고 판정은 상대 증가율로 했다(`#36` 결정)
- **주문당 CPU 가 부하가 늘수록 줄어드는 것**(뗀 쪽 23.5 → 15.9 → 10.8ms)은 요청과 상관없이 시간당 드는 몫(배경 스레드 · GC 등)이 요청 수로 나뉘기 때문이다
- **메모리는 부하와 거의 상관없다.** 가만히 있어도 약 110MB 를 더 쓰고, 부하 중에도 80 ~ 140MB 범위다. 힙이 GC 따라 출렁여 회차마다 수십 MB 흔들린다
- **흔들림** : 서비스 · 부하 12칸 중 11칸에서 붙임 5회의 최솟값이 뗌 5회의 최댓값보다 컸다(나머지 1칸 : 초당 10건 order, 뗌 한 회차가 4.96초로 튐). 차이 자체는 맥북 흔들림보다 크다

## 메모리는 어디에 드나 (NMT, 초당 20건, 붙임 − 뗌)

| 항목 | gateway | order | payment | inventory |
|---|---|---|---|---|
| 클래스 수 | +5,169 | +5,263 | +5,131 | +5,683 |
| Metaspace + Class (클래스 정의) | +25MB | +26MB | +25MB | +28MB |
| Code (JIT 기계어) | +9MB | +9MB | +9MB | +10MB |
| Symbol (클래스 · 메서드 이름표) | +5MB | +5MB | +5MB | +6MB |
| 스레드 수 (스택) | +18 (+2MB) | +15 (+2MB) | +12 (+2MB) | +12 (+2MB) |
| **힙 아닌 쪽 합** | **+45MB** | **+48MB** | **+46MB** | **+53MB** |
| 힙 (committed) | +49MB | +39MB | +56MB | +51MB |
| NMT 합 | +94MB | +87MB | +101MB | +105MB |

- 힙 아닌 쪽 **약 45 ~ 55MB 는 에이전트를 붙이는 한 고정**이다. 대부분 에이전트가 싣는 클래스 약 5,000개
- 힙 몫 약 40 ~ 55MB 는 스팬 · 로그 · 메트릭 객체와 GC 가 힙을 넓게 잡는 몫이다
- inventory 가 늘 가장 크다. Redis(Lettuce · Netty) 계측 클래스가 더 걸린다(클래스 +5,683)

## 어디서 CPU 가 드나 (원인 찾기, 초당 20건, 3회 중앙값)

| 변형 | 주문 1건당 추가 CPU | 에이전트 추가분 중 줄어든 몫 | 메모리 차이 |
|---|---|---|---|
| 그대로 (on, 5회) | +4.22ms | — | +80 ~ +141MB |
| 메트릭 끄기 (`OTEL_METRICS_EXPORTER=none`) | +3.29ms | 약 22% | 그대로 (+82 ~ +131MB) |
| 쓰는 계측만 켜기 (`instr-min`) | +3.86ms | 약 9%, **흔들림과 구분 안 됨** | **약 10 ~ 20MB 줄어듦** (+64 ~ +125MB) |

파일럿(research 5.0 ③) : 샘플링 10% · 로그 끄기 + 메트릭 60초는 거의 효과 없음.

이 표는 다른 표보다 약하다. 원인 찾기 3회씩은 on · off 와 번갈아 돌리지 않고 약 30분 뒤에 이어 돌렸다(그 뒤 `suite.sh` 를 on · metrics-off · instr-min 번갈아로 고쳤다). 주문 1건당 값의 회차별 범위가 on 19.0 ~ 20.8ms, metrics-off 18.7 ~ 19.6ms, instr-min 19.3 ~ 20.3ms 로 겹친다.

- 메트릭 끄기는 **에이전트가 더 쓰는 CPU 의 약 5분의 1** 쯤으로 보인다(범위가 일부 겹쳐 확정은 아님). HTTP · DB 지연 히스토그램은 샘플링과 상관없이 모든 요청에 기록되니 앞뒤가 맞는다
- 나머지 대부분은 **요청마다 계측 코드가 도는 일 자체**(컨텍스트 전파, 헤더 주입, 스팬 시작 · 끝)로 본다. 샘플링을 낮춰도 이 일은 그대로라 안 줄어든다(파일럿)
- 쓰는 계측만 켜기는 CPU 차이가 흔들림 안이다(order 는 오히려 7.69초 → 7.83초). **메모리는 10 ~ 20MB 준다**(네 서비스 모두). 그래도 inventory 는 100MB 를 넘는다
- `instr-min` 으로도 Service map · 트레이스 모양(SERVER · HTTP · DB · Redis 스팬)은 그대로 나왔다(짧은 확인 1회). 단 hikaricp 커넥션 풀 메트릭(`db.client.connections.*`)과 로그 MDC 의 trace_id 주입(logback-mdc) 같은 것은 빠진다

## 요구사항 문장 제안 (backend `docs/design/10-requirements.md`)

> 2026-10-09 팀이 고치기로 했고 아래 제안대로 바뀌었다(backend `#132` · PR #133 · ADR `#56`). 새 기준으로는 초당 20건 +1.4 ~ +2.1%p · 메모리 최대 141MB 로 통과다. 성능이 좋아진 게 아니라 3% 를 무엇 대비로 읽을지 바꾼 것이다.

지금 : "에이전트 오버헤드 — 대상 앱 CPU 3% 이내, 메모리 100MB 이내"

문제 : ① 3% 가 무엇 대비인지 없다(상대 증가율이면 가벼운 앱에서 늘 실패, 절대 %p 면 부하를 고르는 대로 통과) ② 측정 조건(부하 · 제한)이 없다 ③ OTel 에이전트는 클래스만으로 약 50MB 를 고정으로 쓰고, 공식 야간 벤치도 최소 힙이 약 100MB 늘어 100MB 는 기성 에이전트로는 빠듯하다

제안 :

```
에이전트 오버헤드 — 같은 이미지 · 같은 고정 부하에서 에이전트를 뗀 쪽과 비교한다 (perf/overhead, #36)
 · CPU : 주문당 추가 CPU(ms)와 상대 증가율을 함께 보고한다. 파드당 CPU 1개 · 초당 주문 20건(HTTP 약 30건)에서 1코어 대비 +3%p 이내
 · 메모리 : 컨테이너 메모리 증가 150MB 이내 (현재 OTel Java Agent 2.31.1 실측 80 ~ 141MB)
 · 에이전트 버전을 올릴 때마다 같은 명령으로 다시 잰다
```

이 문장이면 지금 값은 통과(초당 20건 +1.4 ~ +2.1%p, 메모리 최대 141MB)지만, 숫자를 결과에 맞춰 올린 것이라는 점을 같이 밝혀야 한다. 원래 숫자(3% · 100MB)를 지키려면 설정을 줄여야 하는데(메트릭 끄기 · 계측 줄이기), 이번 측정으로는 그래도 상대 증가율 3% 와 inventory 100MB 는 못 맞춘다.

## 이번에 안 한 것

- 설정 변경(메트릭 끄기 · 계측 줄이기 · 메트릭 간격) : 다음 이슈. 화면 · Service map 에 영향을 같이 봐야 한다
- k8s 실제 파드에서 재기 : 매니페스트가 생기면 같은 스크립트를 파드 limit 조건으로
- 시작 시간 : 목표에 없어 재지 않았다(공식 벤치 +3.6초, research 2.6)
