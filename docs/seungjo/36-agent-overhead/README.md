## 문제

비기능 요구사항 "대상 앱 CPU 3% 이내, 메모리 100MB 이내" 를 한 번도 재 본 적이 없었다. 3% 가 무엇 대비인지, 어떤 조건에서 재는지도 정해져 있지 않았다.

| 재 본 것 | 값 |
|---|---|
| 측정 기록 | 없음 (FN-10 "부하 테스트로 대신한다" 뿐) |
| compose 의 쇼핑몰 제한 | CPU · 메모리 제한 없음 → JVM 최대 힙 약 4GB, 비교가 GC 타이밍에 묻힘 |
| 에이전트 설정 | 샘플러 `always_on`, 메트릭 10초, 로그 보내기 켬 (가장 비싼 쪽) |

**무엇이 깨지나** : "에이전트만 붙이면 된다"(ADR `#33`)는 제품 전제에 비용 숫자가 없다.

## 선택지

여덟 가지. 전체 표 · 근거는 [`research.md`](research.md) 5 절.

| 항목 | 고른 것 | 버린 것과 이유 |
|---|---|---|
| A. CPU 3% 의 뜻 | **상대 증가율 · 1코어 대비 %p · 요청당 ms 를 다 적고 판정은 상대 증가율** | %p 로 판정 : 부하를 고르는 대로 통과 · 실패가 정해진다 |
| B. 메모리 | **부하 중 cgroup `memory.current` 차이**, 부하 0 · NMT 병기 | `jvm.memory.used` : 뗀 쪽엔 없다 |
| C. 제한 | **서비스마다 CPU 1개 · 1GB** | 제한 없음 : 비교가 흐려진다 |
| D. 힙 고정 | **안 함** | `-Xms` 고정 : 파일럿에서 오히려 더 흔들림 |
| E. 부하 · 반복 | **초당 10 · 20 · 40건 × 붙임 · 뗌 5회 번갈아** | 한 부하만 : 부하 비례를 못 보여 줌 |
| F. 원인 찾기 | **메트릭 끄기 · 쓰는 계측만 켜기 측정만**, 설정 변경은 다음 이슈 | 이번에 설정까지 : 화면 · Service map 영향까지 범위가 커짐 |
| G. 스크립트 | **레포 `perf/overhead/`** | 문서 안 코드 : 다시 돌리기 어려움 |
| H. 요구사항 | **고친 문장을 backend 에 제안**, 고칠지는 팀이 | 그대로 둠 · 설정으로 맞춤 |

## 결정

- **고른 것** : 위 표. 뗀 쪽은 `-javaagent` 를 아예 뺀다(`OTEL_JAVAAGENT_ENABLED=false` 는 jar 를 읽어 조금 남음). CPU 는 cgroup `cpu.stat usage_usec` 구간 차이
- **되돌리는 조건** : 에이전트 버전을 올리거나(3.0) k8s 파드 limit 이 정해지면 같은 스크립트로 다시 잰다

결정 원문은 [`research.md`](research.md) 8 절과 [`prompts.md`](prompts.md).

## 결과

자세한 표는 [`results.md`](results.md), 원자료 [`results.csv`](results.csv).

| 요구사항 | 결과 | 판정 |
|---|---|---|
| CPU 3% 이내 (상대 증가율) | 초당 10 · 20 · 40건에서 +10 ~ +39%. 1코어 대비로는 +0.6 ~ +3.6%p, 주문 1건당(재고 조회 포함) +2.9 ~ +4.3ms | 못 지킴 |
| 메모리 100MB 이내 | +80 ~ +141MB, 부하 0 에서도 +104 ~ +118MB. inventory 는 늘 넘고, 초당 10건에선 네 서비스 모두 넘음 | 못 지킴 (경계) |
| (고친 기준, ADR `#56`) CPU 1코어 대비 +3%p (초당 20건) · 메모리 150MB | +1.4 ~ +2.1%p · 최대 141MB | 통과 (초당 40건이면 CPU 넘음) |

- 메모리 중 약 45 ~ 55MB 는 힙 아닌 쪽(에이전트 클래스 약 5,000개 · JIT 코드, 고정), 나머지는 힙
- 에이전트가 더 쓰는 CPU 의 약 5분의 1 은 메트릭 기록으로 보이고(3회, 범위 일부 겹침), 나머지는 요청마다 도는 계측 자체. 샘플링 10% 는 거의 효과 없음
- 쓰는 계측만 켜면 메모리가 10 ~ 20MB 준다. CPU 차이는 흔들림 안

## 어떻게 확인했나

- 회차 44번(초당 10 · 20 · 40건 붙임 · 뗌 5회씩 30, 부하 0 3회씩 6, 원인 찾기 6, NMT 2) + 파일럿 약 20번. k6 check 실패 0건
- 별도 리뷰(code-reviewer) : REQUEST CHANGES → 반영. HIGH 1 「주문 1건당」 이 실제로는 HTTP 요청 1건당(재고 조회 포함 1.5배 차이)이었다 → 주문 수로 나누게 고침. MEDIUM : 초당 10건 메모리 문장, 원인 찾기 22% · 9% 를 흔들림 안에서 단정 → 낮춤, `suite.sh` 에 부하 0 · 원인 찾기 번갈아 추가, `run.sh` 가 `up` 실패 때 컨테이너를 남김 · k6 가 안 돌아도 0 을 기록 · 가드가 앱 넷만 봄 → 고침. 리뷰가 `summarize.py` 출력과 문서 표가 글자 하나까지 같고 NMT · 회차 수 · 범위 숫자가 원자료와 맞음을 다시 계산해 확인
- 흔들림 : 서비스 · 부하 12칸 중 11칸에서 붙임 최솟값 > 뗌 최댓값
- `instr-min` 에서도 Service map · 트레이스 스팬 모양이 그대로인지 ClickHouse `spans` 로 확인
- 측정 동안 사용자 Collector · Kafka · ClickHouse 는 그대로 두고 쇼핑몰 컨테이너만 띄우고 내렸다

## 이 이슈에서 배운 것 (세 줄)

- "3%" 같은 목표는 무엇 대비인지 정하지 않으면 같은 측정에서 통과도 실패도 쓸 수 있다
- 에이전트 CPU 는 요청당 고정 시간이라 가벼운 앱일수록 비율이 부풀고, 샘플링으로는 줄지 않는다
- 메모리의 절반은 에이전트 클래스라 붙이는 순간 고정으로 든다
